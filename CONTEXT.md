# Context

Glossary for the threat-modeling service. One extraction produces the canonical system model. Every **Framework** the job selected analyses that one model, and every agent downstream reads it as input.

## Glossary

- **System Model** — the canonical, structured representation of the system under analysis. The extraction agent produces it from semi-structured front-end text. One extraction serves every framework a job selected: it is the single source every **Lane Agent** of every selected **Framework** reads, and the one model a **Report** embeds.
- **Element** — any node or edge in the System Model. Exactly five types (classic DFD-based STRIDE-per-element taxonomy): External Entity, Process, Data Store, Data Flow, Trust Boundary.
- **External Entity** — an actor outside the system's control: users, third-party systems.
- **Process** — running code or a component that transforms data. Its **Interface Kind** says what the process presents. `web` covers the HTTP family as an application presents it: a browser UI, a REST, GraphQL or SOAP API, or a websocket. `non-web` covers anything else, and `unknown` means the input does not say. The Interface Kind is not what a connection to the process carries: a **Data Flow**'s `protocol` is a separate fact, and the code never reads one off the other. A **Framework** that scopes itself to web applications reads the Interface Kind.
- **Data Store** — where data rests: databases, buckets, queues-at-rest.
- **Data Flow** — a directed connection that carries data between two elements. There is one flow per interaction. The direction says who starts it, and the response rides implicitly. An independent reverse-direction interaction, such as a webhook or a push, is its own flow.
- **Trust Boundary** — a named trust zone (flat, no nesting): network zones, auth boundaries, privilege levels. Every External Entity, Process, and Data Store belongs to exactly one zone via `trust_zone`.
- **Boundary Crossing** — a derived fact, never extracted. A Data Flow crosses a boundary if, and only if, its endpoints' zones differ. Code computes it, so it cannot contradict the model. It is the strongest input a **Lane Agent** reads.
- **Candidate** — a structural condition a deterministic rule found in the validated System Model and handed to one **Lane Agent** to investigate. It carries a rule ID, the elements it is about, and the model facts that made it fire. The service derives it like a **Boundary Crossing**, and it stands far below one. The rules belong to a **Framework Package** rather than to the service, because the choice of which lane sees a lead is judgement about a framework's own method. Two frameworks therefore read the same model and fire different rules on it. A candidate is not evidence and cannot become a **Claim**: it carries no severity, no attacker action and no assertion that anything is wrong, and nothing downstream of the prompt reads one. It is never a **Ground** either. A claim a candidate led to is grounded in the crossing or the `unknown` attribute the rule read, never in the rule. Rules fire on structure alone — a control attribute's leading token, a zone kind, a fan-in count — so nothing here interprets prose. An agent that investigates a candidate and rejects it gives the intended outcome, and an agent that finds a claim no rule triggered on is the reason the agent exists.
- **Asset** — something worth protecting. It is not an element type. The model records it as tags on Elements from a small controlled vocabulary: `credentials`, `pii`, `financial`, `health`, `secrets`, `business-critical-data`, `availability-critical` and `reputation`. A deployment can extend that list in config. Assets feed impact scoring and skill selection. Detail specific to one system lives in the element's own name and description.
- **Unknown** — a legal attribute value. It means the input neither stated a fact nor allowed the service to infer it. A **Lane Agent** treats an unknown security control as unverified, never as present and never as absent. Uncertainty a speaker *voices* is also `unknown`, whether it is a hedged value ("I think it's OIDC") or an admitted gap ("no idea"): to speak about a fact is not to state it, so this is neither a value nor an **Assumption**. The speaker's words stay verbatim in the element's `notes`, which is what separates a gap somebody probed from a topic nobody raised. Two **Sources** that disagree land here too, wherever the attribute can hold `unknown`: the sources carry equal weight, so the service records the disagreement instead of settling it, and both claims stay verbatim in `notes` beside their labels. What `notes` carries is context for the question a needs-info **Verdict** asks. It is never evidence for a **Claim**, and it never adds weight to a rating: an unknown attribute rates the same whether somebody hedged about it, two people contradicted each other, or nobody raised it.
- **Assumption** — a value extraction inferred, with a stated basis. The service records it on the System Model's top-level assumptions list — the assumption, the element ID, the attribute inferred, and the basis — as well as in the attribute itself. The pair of element and attribute names what the service inferred. An element carries several security-relevant attributes, so an entry that names only the element leaves a reader unable to tell which value the basis covers. The validity gate resolves both, and it requires a real element, an attribute that element declares, and an attribute that holds a value. One entry covers one attribute, so an element with two inferences takes two entries. The entry never copies the value beside them; a reader reads it off the attribute. The gate refuses an assumption on an attribute that still reads `unknown`, because nothing was inferred there and the entry contradicts its own record. `unknown` means the input did not state the fact. An assumption means the service inferred it on the record. It is never a silent guess, and never a *speaker's* guess: the basis is what extraction inferred from what the input supports, so a hedge is never one. Getting that distinction wrong is invisible downstream, because a **Lane Agent** weighs an assumption's value as read from the text. One case comes from the schema rather than from the text. Where two **Sources** disagree on an attribute that *cannot* hold `unknown` — a `trust_zone`, an External Entity's `kind`, or a Data Flow's endpoints — extraction must still emit a legal value. It picks one, and for `trust_zone` it picks the reading that yields a **Boundary Crossing**. It then records an Assumption that names the disagreement. That is not a speaker's guess: the schema forces the inference, and the basis says so.
- **Framework** — one security method this service can analyse a system under, named from a closed vocabulary the code can spell. A job names the frameworks it wants and gets one **Framework Analysis** per name. The service analyses nothing under a framework nobody asked for, and no default set exists anywhere on the path. Frameworks do not see each other. Two of them share the one **Valid System Model** and meet nowhere else. The only relation between their output is that both cite **Element ID**s from that model.
- **Framework Package** — one **Framework** as an object the service can run. It has nine declared members — name, version, **Lane**s, **Candidate** rules, claim record, ID rule, options, precondition and local corpus — plus its text under one root at `frameworks/<name>/`. A package declares what its framework judges and what selects its text. The service keeps what it constructs and what it checks. That line sorted every member: the choice of which lane sees a lead is judgement about a framework's own method, so it moved into the package, while building a **Ground** from an agent's selection is construction, so it stayed in service code. A package is a catalog it does not own plus a profile it does. No member names a requirement set, because a contract that required one would exclude every framework that publishes none. Registration is a table edit and an import, never a path in a config file, because a package writes into a `strong`-tier prompt. The service checks every carried package against its own declaration and against the disk before a **Deployment** finishes constructing, so a package that declares a lane with no prompt cannot reach a model call.
- **Precondition** — what one **Framework** asks of a **Valid System Model** before any of its **Lane**s runs. It is a required member of the **Framework Package**, and the graph runs it once per selected framework, after extraction and before the fan-out. It answers one of three states: `satisfied`, `refuted` or `undecidable`. Only `satisfied` runs the lanes. The two refusing states stay apart, because the remedy differs: `refuted` says do not name this framework for this system, and `undecidable` says the input never said, which the submitter answers by submitting more. A refusal is not a job failure. A job that names two frameworks against a system one of them refuses still gets the other's answer, which is why the gate sits where the topology is still one decision. A refused framework still produces a **Framework Analysis**. That block carries no claims and a **Scope Entry** list that states the reason, because the envelope's own check requires the blocks to answer the job's frameworks with none dropped. STRIDE's precondition is total, since every valid model satisfies it, and the package declares it rather than omitting it, so a framework that does scope itself is the ordinary case rather than the odd one. ASVS's precondition is the tier-0 test its own standard never states: is the target a web application or service?
- **Lane** — one unit of parallel analysis inside a **Framework Package**, and one **Model Tier** call. STRIDE's lanes are its six categories. A package's lanes are ordered, non-empty and unique within that package. The names are the package's own vocabulary rather than a shared one, so two packages may declare a lane of the same name. That is why every graph node and state key carries the framework as well as the lane. The service reports **Coverage** per lane, and one lane is one **Lane Agent**.
- **Claim** — what any **Framework** asserts about the system. It carries an ID, the `(framework, framework_version)` pair that says how to read it, a title, a description, the **Element**s it affects, and the **Grounds** that justify it. It is the neutral record that every package's own record extends. It is also the whole of what a consumer that does not know a framework can be held to, which is what the report's fallback rendering shows. Claim IDs are unique within one Framework Analysis and no further. `id` has no shared grammar across frameworks, so two packages may compose the same string for unrelated things. Every mark that points at a claim sits in the same block as the claim it points at.
- **Threat** — STRIDE's **Claim**. It is the neutral record plus the lane the agent found it in, a severity, a confidence and its mitigations. It is a finding about an attack, which is STRIDE's question rather than every framework's. A framework that rules on requirement applicability asserts something else under the same envelope, which is why the neutral record carries none of these four fields. A Threat always traces to the Elements it affects, and to the **Grounds** that justify raising it.
- **ASVS Level** — which of the three ranked requirement sets of ASVS 5.0 a job is ruled against. It arrives as that framework's job option, and the **Report** records it. The levels are cumulative in use, so a run at level 2 rules on the level 1 and level 2 sets together. An organization chooses the level; the service never derives it. ASVS 5.0 broke the tie between application risk and level and tells the organization to choose, so nothing in a **Valid System Model** picks one and the option carries no default. A job that omits it rejects on the input ladder. A run filtered to one level rules on a subset of the standard, which is a fork of ASVS rather than ASVS, and no output of such a run is a compliance result.
- **ASVS Requirement** — one of the 345 numbered requirements ASVS 5.0.0 publishes. The ASVS **Framework Package** holds them as its own private data. No contract member names them and no service module reads them, because a contract that required a catalog would exclude every framework that publishes none. One chapter of the standard is one **Lane**, so a requirement's chapter decides which lane rules on it. A **Claim** about a requirement carries the standard's own version-safe reference, such as `v5.0.0-1.2.5`, which the service composes from the lane and the key the agent supplied. An ASVS claim rules applicability and never a pass. Verification needs source code, configuration and the people who built the system, and a job here carries prose, so `confirmed` says the requirement applies and the input does not show it satisfied.
- **Disposition** — what a corpus case expects the service to *conclude* about one **ASVS Requirement** it applies. The reference record holds it, and the scorer scores it apart from applicability. It has six values, and none of them is a pass: `not-applicable`, `gap-from-prose`, `needs-more-prose`, `needs-code`, `needs-config` and `needs-people`. It is a relation between a requirement and one submission, never a property of the requirement. The same requirement settles from prose in a case whose description happens to state that the control is absent, and needs source code in a case that says nothing. That is why it lives in the corpus rather than in the package, and why a table keyed by requirement was removed rather than reviewed. The scorer compares it against what a report carries: a **Claim**'s verdict, and a **Scope Entry**'s state and the evidence kind it names. The proposal field that decided the routing is stripped before the payload, so nothing scores against it. The service sets the policy for which kinds become a scope entry and the scorer reads it, so a job that carried source code would score a `needs-code` expectation on the claim path instead. It is eval-side only. No **Framework Package** declares one, because how well a framework must be measured is the eval's business.
- **Ground** — one piece of justification for one **Claim**, in exactly one of five kinds. A `quote` carries verbatim submitter words plus the `source_label` that names the **Source** they came from. An `unknown-attribute` carries an element ID plus the attribute whose **Unknown** value makes the claim raisable. An `absent-attribute` carries the same two fields, for a control attribute whose value states its own absence. A `derived-fact` carries a flow ID whose **Boundary Crossing** is the fact relied on; it is a reference rather than a copy, because the crossing recomputes from the model the report already embeds. An `absent-element` carries a `term`, a word a submitter would write for a thing that no element's free text names. Every claim of every framework carries at least one ground. The five kinds are properties of the shared model and of the submission rather than of any method, which is what keeps them neutral. The two attribute kinds carry identical fields and different facts, so the kind is the only place their difference lives: an unknown is a question the input left open, and the claim that rests on it is conditional, while a stated absence is the input answering that question with *no*, and the claim that rests on it is not. `absent-element` is the one kind whose referent is the whole model rather than a part of it. It is also the one a framework needs to justify a claim about what a system does *not* have, because each of the other four can only name something present. Without it, a requirement ruled out for a component the system never had has no honest fact to cite, and reaches for an unrelated quote instead. An agent names an `absent-element` rather than selecting one, because the **Evidence Catalog** can enumerate what a model holds and never what it lacks. The service checks it the other way round from every other reference: it resolves when nothing in the model names the term, and drops as unresolved when something does. It can therefore never assert an absence the model contradicts, and what it proves is absence from the *description* rather than from the system. There is no free-text kind, because free text would be the escape hatch an agent reaches for exactly when neither a quote nor an unknown exists. A **Lane Agent** chooses a ground and the service constructs it: the agent names an **Evidence Reference** or proposes a quote, and code builds the record, so a ground's kind and its fields can never disagree. The service never derives a ground from the affected elements' **Source Excerpts** either. An excerpt says why an *element* exists and a ground says why a *claim* was raised, so a derived citation would always render *a* quote and often the wrong one. Code checks a quote ground against the bytes of the source it names. That check reads presence only and never support, which stays the Critic's judgement. The service offers a refused quote to the **repair rung** first. Where the source holds a span of the quote's word count, or up to two words more, and near enough in the text, the service rewrites the ground to that span — the submitter's words, never the model's — and a mark keeps what the agent wrote. Otherwise the service marks an unverifiable quote rather than dropping it. The mark lives in the **Framework Analysis** beside the claim rather than inside the Ground, because a field an agent could set about its own honesty is not evidence. A claim where *no* ground verifies is a **Dropped Claim**. The service drops it from the block and marks it there with its title and the quote the check could not find. It never fails the job.
- **Evidence Catalog** — every fact any **Lane Agent** of any selected **Framework** may cite. The service enumerates it from the **Valid System Model** before analysis: each attribute the input left **Unknown**, each control attribute the input states is *absent*, and each **Boundary Crossing**. The absent half covers the five control attributes only, because `none` carries a determinate meaning only where the attribute names a control. `unknown` is the extraction sentinel on every field, and the code reads it by its leading token, so a voiced hedge counts as one. The service derives the catalog rather than extracting it, and derives it twice from the same model rather than passing it between nodes. The set an agent chose from and the set its choice resolves against therefore cannot differ. A catalog entry asserts only that this fact is in the validated system representation. `authentication is unknown` is catalogable; `authentication is weak` has no way in. Whether a catalogued fact takes part in a credible attack stays the agent's judgement and the **Critic**'s to rule on. Quotes are deliberately absent, because choosing a span for what it *states* is a judgement no enumeration can make. The catalog is the service's, and no package extends it. It enumerates the **Valid System Model** rather than any framework, so a framework that needs a fact the model does not hold is describing a gap in the model. That gap is the model's to fix, for every framework at once.
- **Dropped Claim** — a **Claim** the service removed from a **Framework Analysis** because one entry of it was at fault. The block's `dropped_claims` records it, with its title and the fault in the agent's own words. One list holds every reason: the proposal failed its own schema, every **Ground** it cited was lost, every **Element** it named is absent from the model, or its ID repeats an earlier draft's. A fault in one entry of one claim never fails a job. Two things still do: a whole lane that wrote nothing, and a **Critic** whose re-ask did not reconcile.
- **Evidence Reference** — one catalog entry's stable ID: `unknown:<element-id>:<attribute>`, `absent:<element-id>:<attribute>` or `crossing:<flow-id>`. The service builds it from IDs the model already carries, so the same model yields the same IDs on every run. A **Lane Agent** emits one in place of a **Ground**. The agent selects, and the service resolves the ID back into the entry's canonical record. Resolution is exact, with no near match and no repair, because inferring which fact an agent *meant* is the guess the closed set exists to remove. A reference that names nothing is dropped and marked, the way an unverifiable quote is. The claim then stands on whatever else it cited, and a claim left with no grounds at all becomes a **Dropped Claim**, marked with the references it cited. Agents do compose well-formed references to facts the catalog does not hold, and this system nowhere discards six lanes of analysis to punish one citation error.
- **Proposal** — what a **Lane Agent** emits. STRIDE's is a **Threat Proposal**: a finding that carries `evidence_refs` and quote candidates rather than **Grounds**, and its framework's own **ID key**, which for STRIDE is `sequence`, rather than a claim ID or a lane. It is two flat lists that a provider's schema compiler can express exactly, where the conditional field relationship inside a `Ground` cannot be. Nothing an agent puts in either list is therefore a shape error. One neutral resolver turns a proposal into the draft that framework's **Critic** reads. It names no framework: it composes every claim ID from the package's own ID rule, and stamps the lane into whatever field that rule names. The lane is the graph's fact rather than the agent's, because the graph fills in one node per `(framework, lane)` pair before any model runs. A draft's lane, its ID's prefix and the node that produced it therefore agree by construction. Whether a claim *belongs* in the lane the agent found it in is a different question, about content rather than spelling, and it is the Critic's.
- **Lane Agent** — one of a **Framework**'s parallel agents. Each one owns a single **Lane** across all applicable Elements, and STRIDE runs six, one per category. A lane agent emits **Proposal**s: a description, element references, **Evidence References** and quote candidates, plus whatever else its own package's record carries. The service resolves those into drafts. One shared prompt body asks every framework's lane agents for the same object, which is why the field they fill is spelled `claims` rather than in any one method's word. The name says what the agent does, because *analyst* in this repo means the human who reads the report. The graph node names follow, as `analyze_<framework>_<lane>`, while the tier config keys collapse to one `analyze/<framework>`, because a framework's lanes all run the same judgement on the same tier. A lane agent reads the job's **Sources** directly, and a *stripped* System Model: the service removes `source_excerpt`, `source_label` and `source_speaker` from the model it renders. The agent therefore cannot align a quote to an excerpt it can no longer see. The report still carries the excerpts. The honest cost is that the bytes an agent saw are no longer the bytes the report carries.
- **Domain Pack** — subject-matter reference material about a technology family, held in `domains/`. The service selects a pack per job from the System Model's own technology fields, and renders it to every selected framework's **Lane Agents** beside their candidates. Packs are shared rather than packaged, because of their retrieval key: the one System Model that #162 ruled serves every framework is what chooses a pack, so a pack belongs to no package in particular. A pack may name no package's lane. It states a technology's facts, its failure modes and the questions to ask, and a sentence that assigns those to a STRIDE category is a sentence that is false in another framework's prompt. A pack is analysis knowledge and never evidence: it grounds nothing, and caller text decides only *which* repo-authored pack loads, never what one says. The service caps how many load per analysis, because loading every pack into every job spends the largest block in the longest prompt on a system nobody submitted.
- **Reference Note** — one document in a **Framework Package**'s own corpus, at `frameworks/<name>/notes/`, about a single structural condition. It says when the condition applies, what to ask about it, and what it may not be used for. It has the same standing as a **Domain Pack**, and the service selects it differently: by the **Candidate** rules of *that package* that fired in a lane. The material therefore follows this model's leads rather than its technologies, and a lane that triggered nothing receives nothing. That retrieval key is why a note lives in the package: selection is a set intersection over one package's fired rules, so a note the service stored would have no service-side caller. A note is analysis knowledge and never evidence. It is not a fact about the system under review, it is absent from the evidence catalog, and nothing can cite it.
- **Worked Case** — one document in a **Framework Package**'s own corpus, at `frameworks/<name>/cases/`. It records a judgement somebody already made about *another* system: the architecture pattern, the claim considered, whether they accepted or rejected it, why, and what decided it. The service selects it by that package's fired rules, as it selects a **Reference Note**. It stands with the exemplars: it is reasoning to follow, never a conclusion to carry across. Cases are curated and version-controlled, and the service never learns them from production runs, because writing back a run's own output would let one model's mistake become the next model's reference. Several cases end in a rejection on purpose, which is the outcome an exemplar cannot demonstrate.
- **Coverage** — the per-**Lane** account of what deterministic analysis offered a lane, and how much of it that lane's drafts cite. It counts candidates, boundary crossings, unknown controls and elements, each with a cited count. It is per lane rather than per category, because a category is one framework's word for a lane and the account has the same shape for any of them. Code computes it over the **drafts** rather than the ruled claims, and records it on that framework's own **Framework Analysis**. It never sits on the envelope, because it describes one framework's rules rather than the shared model. It exists to separate *examined and cleared* from *never looked at*. It measures citation rather than attention: an agent that read a flow and rightly found nothing cites nothing, so the number that means something is the aggregate across a corpus, never one lane on one case. The denominators alone travel forwards as well, opening each **Lane Agent**'s input — how many elements, crossings and unstated controls a model holds, and how many of a lane's rules ran and fired. A lane cannot make the separation above about itself unless somebody tells it the size of what it was given. The service derives those denominators from the same three calls as the account behind them rather than recomputing them, so the number in the instruction and the number in the report are one fact. The `*_cited` halves cannot travel with them, because they need drafts that do not exist yet. Coverage is never a quota. No number there says how many claims exist, and a lane that inflates its drafts to fill one has misread it, in the direction that costs more than the undercounting it fixes.
- **Scope Entry** — one unit a **Framework** considered and raised no **Claim** about. That framework's **Framework Analysis** records it. It is the positive half of an answer: without it, a reader cannot tell a unit that does not apply from one nobody looked at, which is the distinction **Coverage** makes about lanes. The unit is the framework's own. The neutral answer is the **Lane**, because a lane is the only unit the service knows without reading a catalog it does not own. A package that holds a requirement set answers in requirements instead. Every unit appears, and the service never derives the complement: a scorer that holds the catalog could derive it, and a report's reader cannot. There are three states. `not-applicable` is a finished answer, and it means the unit does not apply to a system of this shape, whether the **Precondition** refused the model or the package's own rules ruled the unit out before its lane ran. `applicable` means the framework considered the unit and raised nothing. `needs-other-evidence` means the unit applies and this job cannot settle it, because the evidence that would settle it is not a kind the job carries. The entry names that kind in `needs`, so a different kind of input can act on the answer. A lane raised such a unit and the fan-in withheld the claim, so it never reaches the **Critic**. Both non-`applicable` states must state a reason, and `needs` is set if, and only if, the state is `needs-other-evidence`. STRIDE's list is empty, which is not an omission: nothing it can analyse is out of scope.
- **Critic** — one **Framework**'s strong-model agent. It reviews the merged union of *that framework's* lane agents' output in one pass, and gives per-claim Verdicts, cross-lane dedupe, and whatever calibration its own method asks for. There is one critic per framework, and two frameworks' drafts never meet. A critic rules its own framework's claims against its own framework's question. A claim duplicated across two frameworks is not a duplicate: it is two methods that reach the same place, which is a result rather than a fault. A critic works from System Model facts rather than free-form reflection, and never from submitter text. It templates against the same stripped model, so the only submitter words it sees are the ones a finding chose to quote. Each critic has its own bounded re-ask, `recritic/<framework>`, pinned to the same tier as the critic it corrects.
- **Verdict** — a **Critic**'s per-claim ruling. It is confirm, reject or needs-info. A rejection carries a reason, which the service keeps for audit. A needs-info is kept and flagged, and says what somebody has to answer. A needs-info uses one of two spellings, and which one is true of the fact rather than a matter of taste. It names an **Element** and one of its attributes where the fact has a place in the **System Model**, or it asks a plain `subject` question where the fact has none. The second spelling exists because a framework may need a fact the model has no slot for, such as whether a policy is documented or what code does, and a framework that rules on requirements answers mostly that kind. It ends a specific failure: a question pointed at the nearest element and whatever attribute happens to resolve passes every check and tells a reader nothing. A rejection also names the check that killed it, in `rejected_because`, from a closed set of three. `evidence` means the draft failed on its own substance. `lane` means somebody filed it against a category or chapter it does not belong to. `duplicate` means another draft already covers it. Those are the Critic's own numbered steps rather than any framework's reasons, which is what keeps the vocabulary neutral: a framework that rules a requirement out of scope and one that rejects an attacker action both answer `evidence`. The rejected set is an audit trail, so the field says which step failed and the reason says what about this draft failed it. The service requires the field of the Critic and not of a report read back. A report written before the field carries no answer, and recording nothing is truthful where inventing a classification the Critic never made is not. Those four rules bind the fields to the `status`, which no provider schema can express, so the service checks them at the review seam rather than on the way out of the **Critic**. A verdict that breaks one is the recritic re-ask's to fix, exactly like a dropped or duplicated ruling, and only a second failure ends the job. The critic therefore emits the unruled shape, and the service builds the ruled one during assembly, so every verdict a report carries satisfies all four by construction.
- **Valid System Model** — one that passes the mechanical well-formedness gate. That gate checks unique typed IDs, referential integrity, zone membership and legal enum values. Lane agents only ever see valid models, and one gate serves every framework, because validity is a property of the model rather than of any method. An invalid extraction gets one Repair Pass, which feeds the validator errors back to a repair node on the same tier. If that fails, the service rejects the job and returns the validator's issues. It rejects rather than *fails*: the input never became a valid model, which is the submitter's to fix, whereas a failure is ours. The service never repairs a model silently.
- **Source** — one piece of untrusted input text a job is built from. It carries a `kind`, a caller-supplied `label`, and the `text` itself. A job carries an ordered, non-empty list of sources, which replaced the single `description` of earlier versions. A transcript-only job is a one-element list, with no special case. `kind` is a closed vocabulary of `description` and `transcript`, and it is load-bearing: it selects the guidance the extraction prompt renders around that source's text, so a new kind means a change to the prompt and the enum together. `label` is unique within a job, is at most 200 characters, and is visible to the model. It is the key a **Source Excerpt** cites, which keeps the traceability chain — threat, then element, then the user's own words, then which source — intact across any number of sources. Order is presentation order only. The contract makes no authority claim, so an earlier source does not override a later one. A job is bounded in UTF-8 bytes rather than tokens, because a token cap would make the contract depend on which vendor a **Deployment**'s tiers select. The bounds are a total across all sources and a source count, both deployment config. There is no per-source byte cap, so an over-budget submission is the *sum*'s fault and the error names no single source. A source reaches a model only inside a delimiter it cannot forge. The service renders one fenced block per source, sized to the content so no submitted text can close its own block, and carries the `label` *inside* the fence so nothing caller-controlled ever sits in instruction position. That render is a pure function of the job, produced once where the graph is driven, so the service and the eval harness cannot show the same job to a model differently.
- **Source Excerpt** — a short quote from the user's input text that an Element was extracted from. Every Element carries one, for traceability and for extraction evals. The chain runs from claim, to element, to the user's own words, to which **Source** spoke them. It travels with a `source_label` that names the Source the *quote* came from, rather than the one the element came from. One verbatim quote has exactly one origin, and an element may draw on several. Where two Sources disagree, the element quotes one claim and the disagreement stays in `notes`. The label is required whenever an excerpt is present, and must be one of the job's labels. A citation that does not resolve asserts a traceability chain that is not there, so the validity gate checks it. An optional `source_speaker` names who spoke the quote, where the text attributes it. It is provenance on a quote, never a role, and never something a **Lane Agent** weighs. It stays its own field so that a name can be stripped, which is impossible once the name is quoted inside the excerpt. The service strips all three fields from the model the lane agents and every **Critic** read. An excerpt answers why an element exists, which is a different question from why a claim was raised, and the second question is a **Ground**'s.
- **Element ID** — a typed, human-readable slug, unique within one System Model (one job): `<type>:<normalized-name>`, e.g. `process:auth-service`. Data Flows use `flow:<source>-to-<dest>:<label>`. Threats reference Elements by these IDs.
- **Graph Run** — one drive of a built pipeline to completion. It is the final session state, plus one record per node execution: which node ran, the build that served it, its **Execution Identity** fingerprint, and its duration. The graph has exactly two drivers, the service over a job and the eval harness over a corpus case, and both obtain a Graph Run from the same place, so provenance never depends on which one ran. The graph cannot loop, so one drive contributes at most one record per node, and a deterministic FunctionNode contributes one that carries no model. One node name carries several records only where several drives accumulate together, as in an eval sweep over its corpus. A Graph Run is distinct from the **Report**: a Graph Run is what happened, and the report is what the service serves. The run's identity fields — job ID, system name and timestamps — come from the driver rather than from the graph.
- **Adversarial Case** — one poisoned source in `evals/adversarial/`, together with what a **Report** over it must and must not contain. It measures robustness, never threat-model quality. The golden corpus in `evals/corpus/` measures the second, and mixing the two would let a robustness regression hide behind a good recall number. The tree is separate for a second reason: a path under `evals/corpus/` makes a whole pull request a **Sitting**, and an adversarial case is a fixture rather than something a voter grades. Code decides every expectation — names that must survive, names the injection asked to invent, verbs it demanded, and whether the model has elements at all — because a model that grades a report produced from a poisoned source reads the same poison. Resistance is a conjunction rather than a score: a run that kept every true fact and also invented a component the attacker named did not partly resist. Every case declares what must survive, because a case that checks only prohibitions is satisfied by an empty answer. At least one case carries no injection at all, because a service that refused everything would otherwise score perfectly. The structural half — that a source cannot close the fence it sits in — is deterministic and runs in CI. The semantic half needs a live model and has never run.
- **Analysis Context** — the third thing a report records about a run, beside what each node *ran on*, which is the **Execution Identity**, and what each finding *rests on*, which is a **Ground**. It is what the service put in front of the **Lane Agents**. It has four parts, recorded in two places, on the rule that a field sits where the thing it describes sits. Two parts describe the run as a whole and stay on the **Report**: a digest of every LLM node's composed instruction, which is a fact about the built graph, and the **Domain Pack**s this job's model earned, which is a fact about the shared model. Two parts describe one framework and sit on its **Framework Analysis**: the **Candidate** rules of that package that fired, and the **Reference Note** and **Worked Case** documents those rules retrieved. The service takes the digest with the job-varying placeholders unexpanded, so it identifies the repo-authored text and carries no submitted bytes. The submission's own digest stays separate, because "which instructions ran" and "which text was analysed" are different questions, and a hash that mixed them could answer neither. Analysis Context is context and never evidence. A pack named here grounded nothing, a rule named here found nothing, and a document named here proves nothing, so reading it as support for a claim reads it backwards. The digest is also gated: it is one of the seven parts of the **Execution Identity**, so a prompt edit re-baselines every **Blessed** fingerprint. That cost was once the argument for recording the digest and not gating it. The argument that won is that a run on edited prompts is not the run a deployment sanctioned.
- **Execution Identity** — what a fingerprint hashes: everything that decided what one node execution could answer. It has seven parts. Six of them decide what the node could answer: the **requested** route this deployment's config asked for; the **served** build, which is the identifier the provider says answered, vendor-prefixed, such as `vertex_ai/claude-opus-5`; how far that served identifier is trusted, which the **vendor** decides: `provider_reported` where the translator reads the build's name out of the response body, and `requested_echo` where it fills the name from the request, so the served half repeats the requested half and adds nothing; its tier's resolved sampling params; the **Analysis Context**'s instruction digest for the graph it ran in; and the installed versions of the distributions between the node and its provider. The seventh is the payload's own schema version, which the service bumps whenever the shape changes, so a fingerprint says which shape it hashed. Both routes are in it, because the served one is the provider's own claim and nothing verifies it. With the served build alone, a compromised translator names a build the deployment already blesses and certifies whatever it likes. The requested half comes from configuration the translator has no say in. The identity is otherwise a property of the **Model Tier** and the graph rather than of a node. The node name is not an input, so two nodes on one tier in one graph that served the same build share one execution identity. The service reads it per node *execution*, so a build that moves part-way through an eval sweep yields two identities for one node. That is the drift signal rather than a defect. No endpoint or region is in it, on any vendor: a region names where a request went, not what decided the answer, and two regions serving one set of weights would give one run two fingerprints for no difference a reader could act on. The version is what makes widening it a re-key rather than a silent change.
- **Report** — the complete payload a finished job serves, and the only thing a caller reads. It holds one job's facts, one **Valid System Model**, and one **Framework Analysis** per framework the job selected. A field sits where the thing it describes sits, and that one rule sorted the flat schema this replaced: what describes the job or the shared model stayed on the envelope, and what describes one framework's output moved into its block. The service enforces self-containment rather than assuming it. The boundary crossings are exactly the ones derived from the embedded model, the element count is that model's own, and the blocks are the job's frameworks in order, with none dropped and none repeated. That is the envelope's version of *no partial report*: a caller who named two frameworks and reads one has no field that would tell them which half is missing. Every claim's checks run against the shared model, once per block, over the neutral **Claim**. A package that narrows its claims therefore narrows what those checks run over, and cannot opt out of them. A consumer that does not know a framework reads that neutral shape and nothing the framework never claimed.
- **Framework Analysis** — one **Framework**'s whole output inside a **Report**. It holds that framework's version, its own disclaimer, its **Claim**s and its rejected claims, its **Coverage**, its marks, and the per-framework half of **Analysis Context**. It is self-contained against the one shared model, and never against a second copy of it: every **Element ID** it cites resolves in the envelope's `system_model`. That is why the design refused one whole report per framework, which would duplicate the largest block after the findings and leave nothing able to check that two embedded copies of one model agreed. Its `disclaimer` is the package's rather than the service's. The envelope's disclaimer says what the service is, and this one says what this framework's claims assert. The two become different sentences the moment a report carries a framework that rules on requirement applicability rather than on attacks. The only relation between two blocks is the **Element ID** both cite. Code computes that join with no model pass, which is why no cross-framework critic exists.
- **Consumption Budget** — the three per-caller bounds a **Deployment** enforces over a rolling window. They are the half the concurrency ceiling cannot reach: how many jobs one token subject may start, how many tokens one subject may commit, and how many tokens every subject may commit together. The ceiling is self-clearing, so a caller who submits serially stays inside it forever while spending without limit. That is the unbounded-consumption half of OWASP LLM10, and it was the integrator's to close until [#503](https://github.com/mstarks01/work-agent/issues/503). The bounds are in tokens and never in currency. A price is vendor data with an expiry date, `evals/` re-prices a sweep after the fact, and a gate cannot re-price a submission it has already refused. A job reserves an estimate at admission: its submitted tokens times every model call its selection implies, derived from `PACKAGES`. The service replaces that reservation with the measured usage the moment the job is terminal, so the estimate can over-count, which it does on purpose, without becoming a cap. A job that nothing measured keeps its reservation. A completed run settles from its report, and a rejected one settles from the nodes that ran before the validity gate refused them. A job that failed part-way through the graph had already paid for every node it reached, so freeing its estimate would make the token bound one that any failing job clears. A window's total is a scan over records rather than a counter, which is what makes double credit and negative credit unrepresentable. The global bound is not the sum of the per-subject ones. It is the provider quota's share, which ten subjects divide rather than multiply, and a refusal on it names no other caller. The service decides all of them inside the same atomic reservation the ceiling uses, so no two can be raced apart.
- **Deployment** — one installation of this service together with the configuration it runs on. That is five files — `model_tiers.toml`, `sampling.toml`, `resilience.toml`, `blessed-fingerprints.toml` and `frameworks.toml` — plus three text roots: the shared prompt bodies, the **Domain Pack**s, and one **Framework Package** per framework carried. An `ANALYSIS_*` variable locates each one. That variable picks *which* file the service reads, and never layers a second file over it. `frameworks.toml` fixes what this install carries. A job selects from that set and must name its choice. The file holds no default, because a default set would make one submission mean different things on two installs, with the caller reading no sign of it. The service resolves a Deployment once per process and shares it with everything that runs analysis. The HTTP service, the first-run app and an eval sweep therefore cannot sit on different configurations of the same install, and the manifest a job is certified against is the same object the report route enforces, by construction rather than by two loads agreeing. The service builds a graph for one framework selection, because the nodes, the state keys and the instruction digest are all functions of it. A deployment that serves several selections composes several graphs and reuses each. Loading fails closed, and the package gate runs on the same path: a deployment either has a usable configuration and well-formed packages, or it refuses to start. Its credentials are not part of it, because the service derives them from the vendor each **Model Tier** selects.
- **Attestation** — a detached Ed25519 signature over a **Report**'s versioned canonical form, by a key one **Deployment** holds. It answers the two questions the report's own hashes cannot: which deployment produced this report, and whether any covered byte has moved. Those hashes are unkeyed, and anyone who edits the report recomputes them too, so they establish internal consistency and nothing about origin. A valid signature is authenticity. It is never correctness and never Certification. A signed uncertified report is an ordinary thing, and reading a green signature as an endorsement of the analysis reads it backwards. The signature covers the report *digest*, bound to the canonicalization version, the payload type and the key id. Nobody can therefore lift it onto another document, replay it under another canonicalization, or re-attribute it to another key. Verification has six values rather than two. An unsigned report is an ordinary artifact from a deployment that does not sign. An unknown-key report may be good to somebody with a fuller keyring. A revoked report is a signature that checks out and must still be refused. Rotation and revocation are different events. A retired key still verifies what it signed before it retired, because refusing it would invalidate every historical report on the day a deployment rotated. A revoked key verifies nothing at all, because an attacker who holds it could backdate. One keyring names one key once: two entries under one id would make a first-match lookup decide which status applies, so the keyring refuses the file instead.
- **Blessed** — an **Execution Identity** recorded in a deployment's `config/blessed-fingerprints.toml`, because a sanctioned, measured run produced it. The list is keyed by tier. It is deployment-local and ships empty, and nothing in this repository is blessed on anyone's behalf. Every part of the identity re-baselines it. A prompt edit, a `litellm` bump or a service release moves every fingerprint, and runs read as uncertified until a sanctioned sweep blesses the new ones. That is the cost of a complete identity. It is better than reporting a run on edited prompts as the run that was sanctioned.
- **Promotion** — the write half of Certification. It takes a reviewed eval sweep and records two things in this **Deployment**'s files: the configuration the sweep measured, re-pinned in place in `sampling.toml`, and the Execution Identities that configuration produced, in `blessed-fingerprints.toml`. Its inputs are observations and never assertions. It recomputes every fingerprint from the **Execution Identity** the sweep observed, and reads every part of that identity out of the run artifact's provenance block rather than off the promoting machine. An operator can therefore neither supply a fingerprint directly nor have the *requested* route stand in for the build that answered. Those are different claims, and provider-side routing is what makes the difference matter. Where more than one build answered for one tier, promotion refuses and asks which to bless rather than choosing. That choice selects among what the sweep observed, and cannot introduce anything else. Promotion is additive: a blessed identity stays blessed until a human removes it.
- **Certification** — the three-state result of checking a run's Execution Identities against that blessed list. **certified** means every observed fingerprint is blessed. **uncertified** means at least one is not, and the result reports it by node and hash. **unexercised** means a tier the built graph declares presented no fingerprint at all. One function has two callers, the eval CLI over a sweep and the service over each job it completes, so this is not "the eval gate's" result. Unexercised is an internal assertion rather than a routine outcome: every tier has a node that always runs, and a run that produces no report is never certified. Certification never rides the report. The report carries the raw fingerprints, which are evidence and recompute from the report alone. Certification is a claim about one *deployment's* list, and it lives on the job record. It is never called a verdict, because that word belongs to the Critic.
- **Baseline** — a set of eval sweeps of one configuration, kept in the repository together with their reports. **Review Sitting**s and published numbers read it as their record. Code computes its identity from the sweeps, and a person never types it. The identity has five parts: the clean repository commit, the corpus digest, the requested model per tier, the resolved sampling per tier, and the framework selection. Two sweeps that agree on all five parts belong to one Baseline. The served build a provider answered with is a recorded fact about a sweep, and never part of the identity.
- **Ledger** — the append-only record of what a person decided about a finding. It is the only human judgement the repository holds, and every published quality number rests on it. No row changes and no row is removed. A reviewer who changes a decision appends a new vote, and the latest vote for a `(fingerprint, voter)` pair is the live verdict, so every past state reconstructs. Each voter's votes live in one file that carries that voter's GitHub login, so two contributors' pull requests never touch the same file, and order carries meaning only inside one voter's history. A vote stores the components of its fingerprint, so a better match rule re-keys the ledger by recomputation and costs no re-vote.
- **Review Sitting** — one vote session over a **Baseline**. A person reads its reports, decides on each finding, and appends votes to the **Ledger**. `evals/VOTING.md` holds the procedure. A Review Sitting produces votes and nothing else. It never signs off a corpus case, because that act is a **Case Sitting**.
- **Case Sitting** — one person's read of one corpus case: the sources, the blessed **System Model** and every declared framework's reference set, together in one session. The reader writes their own threat list before they open the recorded sets, so the sets are tested rather than confirmed, and then marks every recorded finding `agree`, `reject`, `duplicate` or `unsure`. A sitting that leaves one unmarked does not record: a set nobody judged is a set nobody tested. `unsure` is a real answer and is counted as one, the same word a **Ledger** vote spells for the same thing, on the same key — the reader read the finding and cannot decide. It exists so that a reader who cannot judge one entry says so, rather than picking one of the other three to get past it. The record is **one JSON file** under `evals/review/submissions/`, named for its own digest, carrying the reader's own list, their marks, their missing list, their notes and a digest of each file they read. A pull request that contributes one carries that file and nothing else, so a sitting rewrites no case, no list and no roster. It holds two names. `submitted_by` is the GitHub login of the account whose pull request carries the sitting, and contribution CI binds it to the account that opened the pull request. `submitted_for` is who read the case: the same login, or `anonymous` where an account carries a read for somebody whose own policy stops them taking part under their name; it is provenance and grants nothing. **Coverage is per Framework.** A sitting covers the frameworks whose reference sets it read, and a case reads as read when every framework it declares is covered. So a case that gains a **Framework Package** waits for that one set, and the sittings already merged still stand: nobody judges a set that did not exist when they read. A change to a read file makes the covering sitting stop covering, so exactly the frameworks whose evidence moved go back and the rest hold. Which frameworks are covered has one reader, `evals/review_submission.current_reviews`, and the rail, the CI gate and the printed count all ask it. A reader who returns for a new framework keeps the list they wrote blind, because a list written now would be evidence of an order that did not happen. A reader holds a sitting on one of two surfaces: the local app, or a standalone page they open offline in a browser and return as one **Sitting Envelope**. Both surfaces call the act a *review* in the words a reader sees, by decision: the reader's word is the plain one, and this glossary's is the one the code and the guides use. `evals/BLESSING.md` step 6 defines the method.
- **Draft Sitting** — a **Case Sitting** a reader started and did not yet submit. It holds the reader's own threat list, their marks, their missing list and their notes, plus a digest of each required file as it stood when the draft opened. It lives outside the repository and never merges, which is what keeps an unsigned own list out of a pull request. It is `open` until the reader records the sitting, and `finished` until they submit. **Recording writes nothing into the working tree**: a sitting becomes a record by merging as one submission, so a reader who stops has nothing to clean up and a surface has nothing to undo. A successful contribution deletes the draft. A finished draft re-opens its case, because the draft is what makes a case re-openable rather than the signature: the reader records the case again, and the second record corrects the first.
- **Sitting Envelope** — one reader's whole offline session as one JSON file. It holds their own list, their marks, their missing list and their notes per case, with the digest of each file as it stood when the page was built. It is also the save file, so a reader who works over several days stops by downloading it and carries on by loading it back. It records answers, and never digests that merge: the import recomputes those from the operator's own tree, and a file that changed under the read refuses its case rather than signing words nobody saw. It crosses a trust boundary, so every field is bounded and every case id resolves against the corpus.
- **Standing** — the class a person's judgement carries: `maintainer` or `contributor`. A person has one standing, whatever they submit, whether that is a vote, a **Case Sitting** or a baseline sweep. The standing lives in a checked-in roster keyed by GitHub login, and never on a vote row or a manifest entry. A promotion therefore re-classes that person's whole history at once and rewrites no row. Every published number states which standings it includes, and contributor judgements stay a second series until a maintainer promotes them.
- **Model Tier** — one of three vendor-neutral classes every LLM node runs on. `base` is the workhorse, and runs extraction and repair. `strong` is judgement, and runs every framework's **Lane Agent**s and, by default, its **Critic** and recritic re-ask. `review` is a place criticism can be bound to instead. The keys are per framework rather than per lane — `analyze/<framework>`, `critic/<framework>` and `recritic/<framework>` — because a framework's lanes all run the same judgement on the same tier, and what an operator chooses between is running one framework's analysis more cheaply than another's. A `recritic` must resolve to its own `critic`'s tier, because a re-ask on a cheaper model than the pass it corrects is the failure that pairing exists to stop. `base` and `strong` are named on a capability axis rather than a vendor's product line; the earlier `flash` and `pro` were Gemini product names. `review` is the exception, and names a place rather than a capability. It is not stronger and not cheaper. It exists so an operator can move a critic off the model it checks, which with two tiers meant running criticism on `base`. Each tier selects its own `(vendor, model)`, and every tier must select one. Only a tier the node map binds builds an adapter, so selecting `review` costs no credential until something runs on it. The service derives auth from the vendor rather than reading it alongside: each vendor owns its credential mode, so nobody can write down an unrepresentable pairing such as `vertex + api_key`.
- **Review Independence** — how far a **Deployment** requires each framework's **Critic** to sit from the analysis it checks. `shared` requires nothing, and is what ships. `distinct_model` requires a different `(vendor, model)` pair. `distinct_provider` requires a different vendor as well. A deployment states it in `model_tiers.toml`, and there is no default, because inheriting `shared` is how an install that meant to review itself independently ends up not doing so and reporting nothing unusual. It bounds correlated failure and never inaccuracy. A critic on the analysis model still catches inconsistency and unsupported claims, and no measurement here says a second provider finds more, so a deployment that reads `distinct_provider` as "more correct" has read it backwards. A policy the tier selections do not satisfy is a load-time refusal that names the framework, rather than a report warning. A deployment that asked for an independent reviewer and did not get one has a configuration to fix rather than a run to annotate. The **Report** records the policy, so a reader of a `shared` run sees that the review was same-domain, and the per-node routes behind it are already on each node's record. It sits deliberately outside the **Execution Identity**: the loader has already enforced it, so hashing it would re-baseline every **Blessed** identity on a policy edit that moved no model.
- **Provider Capability** — what one `(vendor, model)` pair will accept, in exactly three states. **supported** means the provider accepts it, and the pinned model map is what says so. **unsupported** means the provider rejects it. **unknown** means the pinned map carries no entry for the model, so nothing here has an answer. The third state is the load-bearing one, and it never collapses into the second. LiteLLM answers for an unmapped model out of the provider's *base* config rather than declining, so "rejected" and "never heard of it" reach a raise-or-no-raise gate as the same non-raise. That fallback is correct for a **Model Gate**, whose job is to refuse a binding rather than to know things. It becomes a false assurance the moment somebody reports it as a checked answer. A pair that reports `unknown` still binds, because refusing to run a model the map has not caught up with is the worse failure, but nothing has verified it. Capabilities differ between providers legitimately, and the service never equalises them. Inventing a default for an unsupported control, or emulating one without disclosure, is the failure this vocabulary exists to name.
- **Provider Conformance** — whether the *application* behaves equivalently on a given provider. That is a different question from how good that provider's threat models are. Conformance is deterministic, and the suite asserts it for every supported vendor equally. It covers binding, the build-time gates, sampling resolution, **Execution Identity** and the report schema. Model quality is empirical, lives in `evals/`, and is expected to differ. A vendor never fails conformance for scoring lower than another. The suite is credential-free by construction: capabilities come from the pinned model map, and the service builds bindings against a declared-but-fake environment. That is what lets it run for every vendor in the offline lane, rather than only where credentials happen to exist. Its limit is as important as its coverage. It establishes what a provider *would be asked for*, and never that a provider has served a request. The **Provider Smoke** answers that second question. Where its credentials are absent, the coverage stays **unexercised** in the sense Certification already gives the word, and the suite reports it as such rather than leaving a green check to imply otherwise.
- **Provider Smoke** — one small system, once, through the shipped graph, on the pair a deployment selects. It is the cheapest run that can show a provider actually served this application. It runs every framework the deployment carries, because each brings its own tier keys that an operator may point at different vendors, and smoking one while reporting green would leave another's binding unexercised. It answers eight questions and no others: binding, structured extraction, lane-agent output, critic output, sampling acceptance, served-model capture, **Execution Identity**, and a provenance record that recomputes from itself. It answers them for every supported vendor on the same trigger, because coverage that exists only where credentials happen to exist is how one vendor comes to be better assured than the others. Its answers have three values, for the same reason **Provider Capability**'s do: a question the provider left unanswered, such as a response that carries no served build, reports `unknown` and fails nothing, because the application handled the difference correctly. It is not an eval and never grades a threat model. A vendor whose analysis is weaker passes the smoke, and a vendor that has not run one is unexercised rather than failing.
