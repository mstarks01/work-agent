# Context

Glossary for the threat-modeling service. One extraction produces the canonical system model; every **Framework** the job selected analyses that one model, and every downstream agent takes it as input.

## Glossary

- **System Model** — the canonical, structured representation of the system under analysis, produced by the extraction agent from semi-structured front-end text. **One extraction serves every framework a job selected**: the single source every **Lane Agent** of every selected **Framework** consumes, and the one model a **Report** embeds.
- **Element** — any node or edge in the System Model. Exactly five types (classic DFD-based STRIDE-per-element taxonomy): External Entity, Process, Data Store, Data Flow, Trust Boundary.
- **External Entity** — an actor outside the system's control: users, third-party systems.
- **Process** — running code or a component that transforms data. Its **Interface Kind** says what it presents: `web` for the HTTP family as an application presents it (a browser UI, a REST, GraphQL or SOAP API, a websocket), `non-web` for anything else, `unknown` when the input does not say. **This is not what any connection to it carries** — a **Data Flow**'s `protocol` is a separate fact, and neither is ever read off the other. A **Framework** that scopes itself to web applications reads the Interface Kind.
- **Data Store** — where data rests: databases, buckets, queues-at-rest.
- **Data Flow** — a directed connection carrying data between two elements. One flow per interaction; direction = who initiates, the response rides implicitly. An independent reverse-direction interaction (webhook, push) is its own flow.
- **Trust Boundary** — a named trust zone (flat, no nesting): network zones, auth boundaries, privilege levels. Every External Entity, Process, and Data Store belongs to exactly one zone via `trust_zone`.
- **Boundary Crossing** — a derived fact, never extracted: a Data Flow crosses a boundary iff its endpoints' zones differ. The highest-signal input a **Lane Agent** reads, computed mechanically so it cannot contradict the model.
- **Candidate** — a structural condition a deterministic rule found in the validated System Model and handed to one **Lane Agent** as something to investigate: a rule ID, the elements it is about, and the model facts that made it fire. Derived like a **Boundary Crossing** and standing far below one. The rules belong to a **Framework Package** rather than to the service — deciding which lane sees a lead is judgement about a framework's own method — so two frameworks read the same model and fire different rules on it. A candidate is **not evidence and cannot become a Claim**: it carries no severity, no attacker action and no claim that anything is wrong, nothing downstream of the prompt reads one, and it is never a **Ground** — a claim a candidate led to is grounded in the crossing or the `unknown` attribute the rule read, never in the rule. Rules fire on structure only (a control attribute's leading token, a zone kind, a fan-in count), so nothing here interprets prose. Investigating a candidate and rejecting it is the intended outcome, and an agent finding a claim no rule triggered on is the reason the agent exists.
- **Asset** — something worth protecting. Not an element type: modeled as tags on Elements from a small controlled vocabulary (`credentials`, `pii`, `financial`, `health`, `secrets`, `business-critical-data`, `availability-critical`, `reputation`; config-extendable). Feeds impact scoring and skill selection; system-specific detail lives in the element's own name/description.
- **Unknown** — a legal attribute value meaning the input neither stated nor allowed inference of a fact. A **Lane Agent** treats an unknown security control as unverified, never as present or absent. Uncertainty a speaker *voices* — a hedged value ("I think it's OIDC") or an admitted gap ("no idea") — is also `unknown`, not a value and not an **Assumption**: speaking about a fact is not stating it. Their words are kept verbatim in the element's `notes`, which is what distinguishes a gap someone probed from a topic nobody raised. Two **Sources** that disagree land here too wherever the attribute can hold it: equal weight means a disagreement is recorded rather than adjudicated, so the value is `unknown` and both claims are quoted verbatim in `notes` beside their labels. What `notes` carries either way is context for the question a needs-info **Verdict** asks — never evidence for a **Claim**, and never weight on a rating: an unknown attribute rates identically whether someone hedged about it, two people contradicted each other, or nobody raised it at all.
- **Assumption** — a value extraction inferred with a stated basis. Recorded on the System Model's top-level assumptions list (assumption, element ID, basis) as well as in the attribute itself. Unknown = not stated; Assumption = inferred on the record. Never a silent guess — and never a *speaker's* guess: the basis is what extraction inferred from what the input supports, so a hedge is never one. That distinction is invisible downstream if it is got wrong, because a **Lane Agent** weighs an assumption's value as read from the text. One case arises from the schema rather than from the text: where two **Sources** disagree on an attribute that *cannot* hold `unknown` — a `trust_zone`, an External Entity's `kind`, a Data Flow's endpoints — extraction must still emit a legal value, so it picks one (for `trust_zone`, the reading that yields a **Boundary Crossing**) and records an Assumption naming the disagreement. That is not a speaker's guess after all: the schema, not the speaker, forces the inference, and the basis says so.
- **Framework** — one security method this service can analyse a system under, named from a closed vocabulary the code can spell. A job names the frameworks it wants and gets one **Framework Analysis** per name; nothing is analysed under a framework nobody asked for, and there is no default set anywhere on the path. Frameworks do not see each other: two of them share the one **Valid System Model** and meet nowhere else, and the only relation between their output is that both cite **Element ID**s from that model.
- **Framework Package** — one **Framework** as an object the service can run: nine declared members (name, version, **Lane**s, **Candidate** rules, claim record, ID rule, options, precondition, local corpus) plus its text under one root at `frameworks/<name>/`. **A package declares what its framework judges and what selects its text; the service keeps what it constructs and what it checks.** That line sorted every member: deciding which lane sees a lead is judgement about a framework's own method and moved into the package, while building a **Ground** from an agent's selection is construction and stayed service code. A package is a catalog it does not own plus a profile it does — no member names a requirement set, because a contract that required one would exclude every framework that publishes none. Registration is a table edit and an import, never a path in a config file: a package writes into a `strong`-tier prompt. Every carried package is checked against its own declaration and against the disk before a **Deployment** finishes constructing, so a package declaring a lane with no prompt cannot reach a model call.
- **Precondition** — what one **Framework** asks of a **Valid System Model** before any of its **Lane**s runs, declared as a required member of its **Framework Package** and run once per selected framework by the graph, after extraction and before the fan-out. It answers one of three states: `satisfied`, `refuted`, or `undecidable`. **Only `satisfied` runs the lanes**, and the two refusing states are never collapsed, because the remedy differs — `refuted` says do not name this framework for this system, and `undecidable` says the input never said, which the submitter answers by submitting more. A refusal is **not a job failure**: a job naming two frameworks against a system one of them refuses still gets the other's answer, which is why the gate sits where the topology is still one decision. A refused framework still produces a **Framework Analysis**, carrying no claims and a **Scope Entry** list stating the reason, because the envelope's own check requires the blocks to answer the job's frameworks with none dropped. STRIDE's is total — every valid model satisfies it — and it is declared rather than absent, so a framework that does scope itself is the ordinary case rather than the odd one. ASVS's is the tier-0 test its own standard never states: is the target a web application or service?
- **Lane** — one unit of parallel analysis inside a **Framework Package**, and one **Model Tier** call: STRIDE's lanes are its six categories. Ordered, non-empty and unique within a package, and a package's own vocabulary rather than a shared one — two packages may legitimately declare a lane of the same name, which is why every graph node and state key carries the framework as well as the lane. **Coverage** is reported per lane, and one lane is one **Lane Agent**.
- **Claim** — what any **Framework** asserts about the system: an ID, the `(framework, framework_version)` pair that says how to read it, a title, a description, the **Element**s it affects, and the **Grounds** that justify it. The neutral record every package's own record extends, and the whole of what a consumer that does not know a framework can still be held to — which is exactly what the report's fallback rendering shows. Claim IDs are unique **within one Framework Analysis** and no further: `id` has no shared grammar across frameworks, so two packages composing the same string for unrelated things is legal, and every mark that points at a claim sits in the same block as the claim it points at.
- **Threat** — STRIDE's **Claim**: the neutral record plus the lane it was found in, a severity, a confidence and its mitigations. A finding about an attack, which is STRIDE's question and not every framework's — a framework ruling on requirement applicability asserts something else under the same envelope, which is why the neutral record carries none of these four. Always traceable to the Element(s) it affects, and to the **Grounds** that justify raising it.
- **ASVS Level** — which of the three ranked requirement sets of ASVS 5.0 a job is ruled against, supplied as that framework's job option and recorded on the **Report**. The levels are cumulative in use: a run at level 2 rules on the level 1 and level 2 sets together. **Chosen, never derived.** ASVS 5.0 broke the tie between application risk and level and tells the organization to choose, so nothing in a **Valid System Model** picks one and the option carries no default — a job that omits it rejects on the input ladder. A run filtered to one level rules on a subset of the standard, which is a fork of ASVS rather than ASVS, and no output of such a run is a compliance result.
- **ASVS Requirement** — one of the 345 numbered requirements ASVS 5.0.0 publishes, held as the ASVS **Framework Package**'s own private data. No contract member names it and no service module reads it, because a contract that required a catalog would exclude every framework publishing none. One chapter of the standard is one **Lane**, so a requirement's chapter decides which lane rules on it, and a **Claim** about it carries the standard's own version-safe reference — `v5.0.0-1.2.5` — composed by the service from the lane and the key the agent supplied. **An ASVS claim rules applicability and never a pass**: verification needs source code, configuration and the people who built the system, and a job here carries prose, so `confirmed` says the requirement applies and the input does not show it satisfied.
- **Ground** — one piece of justification for one **Claim**, in exactly one of four kinds: a `quote` (verbatim submitter words plus the `source_label` naming the **Source** they came from), an `unknown-attribute` (an element ID plus the attribute whose **Unknown** value is what makes the claim raisable), an `absent-attribute` (the same two fields, for a control attribute whose value *states its own absence*), or a `derived-fact` (a flow ID whose **Boundary Crossing** is the fact relied on — a reference, never a copy, since the crossing recomputes from the model the report already embeds). Every claim of every framework carries at least one; the four kinds are properties of the shared model and of the submission rather than of any method, which is what lets them stay neutral. **The two attribute kinds carry identical fields and different facts**, so the kind is the only place their difference lives: an unknown is a question the input left open and the claim resting on it is conditional, while a stated absence is the input answering that question with *no* and the claim resting on it is not. There is no free-text kind, because free text would be the escape hatch reached for exactly when neither a quote nor an unknown exists. **Chosen by a Lane Agent, constructed by the service**: the agent names an **Evidence Reference** or proposes a quote, and code builds the record, so a ground's kind and its fields can never disagree. Never derived from the affected elements' **Source Excerpts** either: an excerpt says why an *element* exists, a ground says why a *claim* was raised, and a derived citation would always render *a* quote and frequently the wrong one. A quote ground is checked mechanically against the bytes of the source it names — presence only, never support, which stays the Critic's judgement. A refused quote is offered to the **repair rung** first: where the source holds a span of the quote's word count or up to two more and near enough in text, the ground is rewritten to that span — the submitter's words, never the model's — and a mark keeps what the agent wrote. Otherwise an unverifiable quote is **marked, not dropped**: the mark lives in the **Framework Analysis** beside the claim rather than inside the Ground, because a field an agent could set about its own honesty is not evidence. A claim where *no* ground verifies is a **Dropped Claim**: dropped from the block and marked there with its title and the quote the check could not find, never a failed job.
- **Evidence Catalog** — every fact any **Lane Agent** of any selected **Framework** may cite, enumerated from the **Valid System Model** before analysis: each attribute the input left **Unknown**, each control attribute the input states is *absent*, and each **Boundary Crossing**. The absent half is confined to the five control attributes, because `none` carries a determinate meaning only where the attribute names a control, while `unknown` is the extraction sentinel on every field and is read by its leading token so a voiced hedge counts as one. Derived, never extracted, and derived twice from the same model rather than passed between nodes, so the set an agent chose from and the set its choice is resolved against cannot differ. A catalog entry asserts only *this fact is in the validated system representation* — `authentication is unknown` is catalogable, `authentication is weak` has no way in, and whether a catalogued fact participates in a credible attack stays the agent's judgement and the **Critic**'s to rule on. Quotes are deliberately absent: choosing a span for what it *states* is the judgement no enumeration can make. **The catalog is the service's and no package extends it**: it enumerates the **Valid System Model** rather than any framework, so a framework needing a fact it does not hold is describing a gap in the model, which is the model's to fix for every framework at once.
- **Dropped Claim** — a **Claim** the service removed from a **Framework Analysis** for a fault in one entry of it, recorded in the block's `dropped_claims` with its title and the fault in the agent's own words. One list for every reason: the proposal failed its own schema, every **Ground** it cited was lost, every **Element** it named is absent from the model, or its ID repeats an earlier draft's. No fault in one entry of one claim fails a job; what still does is a whole lane that wrote nothing, or a **Critic** whose re-ask did not reconcile.
- **Evidence Reference** — one catalog entry's stable ID, `unknown:<element-id>:<attribute>`, `absent:<element-id>:<attribute>` or `crossing:<flow-id>`, built from IDs the model already carries so the same model yields the same IDs on every run. What a **Lane Agent** emits in place of a **Ground**: it selects, and the service resolves the ID back into the entry's canonical record. Resolution is exact — no near match and no repair, because inferring which fact an agent *meant* is the guess the closed set exists to remove — and a reference naming nothing is **dropped and marked**, the way an unverifiable quote is: the claim stands on whatever else it cited, and a claim left with *no* grounds at all is a **Dropped Claim**, dropped and marked with the references it cited. Agents compose well-formed references to facts the catalog does not hold, and discarding six lanes of analysis to punish one citation error is a trade this system makes nowhere.
- **Proposal** — what a **Lane Agent** actually emits, and STRIDE's is a **Threat Proposal**: a finding carrying `evidence_refs` and quote candidates rather than **Grounds**, and its framework's own **ID key** — STRIDE's `sequence` — rather than a claim ID or a lane. Two flat lists a provider's schema compiler can express exactly, where the conditional field relationship inside a `Ground` cannot be, so nothing an agent can put in either is a shape error. One neutral resolver turns a proposal into the draft that framework's **Critic** reads — it names no framework, composing every claim ID from the package's own ID rule and stamping the lane into whatever field that rule names. The lane is the graph's fact rather than the agent's — one node per `(framework, lane)` pair, filled in before any model runs — so the lane is stamped and the ID composed from it during resolution, by one neutral resolver that reads the package's own ID rule and names no framework. A draft's lane, its ID's prefix and the node that produced it therefore agree by construction. Whether a claim *belongs* in the lane it was found in is a different question, about content rather than spelling, and it is the Critic's.
- **Lane Agent** — one of a **Framework**'s parallel agents, each owning a single **Lane** across all applicable Elements; STRIDE runs six, one per category. Emits **Proposal**s — description, element refs, **Evidence References** and quote candidates, plus whatever else its own package's record carries — which the service resolves into drafts. Every framework's lane agents are asked for the same object by one shared prompt body, which is why the field they fill is spelled `claims` rather than in any one method's word. Named for what it does: *analyst* in this repo means the human reading the report, and the graph node names (`analyze_<framework>_<lane>`) follow, while the tier config keys collapse to one `analyze/<framework>` because a framework's lanes all run the same judgement on the same tier. It reads the job's **Sources** directly and a *stripped* System Model — `source_excerpt`, `source_label` and `source_speaker` are removed from the model rendered to it — so it cannot align a quote to an excerpt it can no longer see. The report still carries the excerpts; the honest cost is that the bytes an agent saw are no longer the bytes the report carries.
- **Domain Pack** — subject-matter reference material about a technology family (`domains/`), selected per job from the System Model's own technology fields and rendered to every selected framework's **Lane Agents** beside their candidates. Shared rather than packaged, because its retrieval key is: a pack is chosen by the one System Model that #162 ruled serves every framework, so it belongs to no package in particular. **A pack may name no package's lane** — a pack states a technology's facts, its failure modes and the questions to ask, and a sentence assigning those to a STRIDE category is a sentence that is false in another framework's prompt. Analysis knowledge, never evidence: a pack grounds nothing, and caller text decides only *which* repo-authored pack loads, never what one says. Capped per analysis, because loading every pack into every job spends the largest block in the longest prompt on a system nobody submitted.
- **Reference Note** — one document in a **Framework Package**'s own corpus (`frameworks/<name>/notes/`) about a single structural condition: when it applies, what to ask about it, and what it may not be used for. Same standing as a **Domain Pack** and selected differently — by the **Candidate** rules of *that package* that actually fired in a lane, so the material follows this model's leads rather than its technologies, and a lane that triggered nothing receives nothing. That retrieval key is why it lives in the package: selection is a set intersection over one package's fired rules, so a note the service stored would have no service-side caller. Analysis knowledge, never evidence: a note is not a fact about the system under review, is absent from the evidence catalog, and can be cited by nothing.
- **Worked Case** — one document in a **Framework Package**'s own corpus (`frameworks/<name>/cases/`) recording a judgement someone already made about *another* system: the architecture pattern, the claim considered, whether it was accepted or rejected, why, and what decided it. Selected by that package's fired rules like a **Reference Note**, and standing with the exemplars — reasoning to follow, never a conclusion to carry across. Cases are **curated and version-controlled, never learned from production runs**: writing back a run's own output would let one model's mistake become the next model's reference. Several end in a rejection on purpose, which is the outcome an exemplar cannot demonstrate.
- **Coverage** — the per-**Lane** account of what deterministic analysis offered a lane and how much of it that lane's drafts cite: candidates, boundary crossings, unknown controls and elements, each with a cited count. Per lane rather than per category, because a category is one framework's word for a lane and the account is the same shape for any of them. Computed in code over the **drafts** rather than the ruled claims, and recorded on that framework's own **Framework Analysis** — never on the envelope, since it describes one framework's rules rather than the shared model. It exists to separate *examined and cleared* from *never looked at* — and it measures **citation, not attention**: an agent that read a flow and rightly found nothing cites nothing, so the number that means something is the aggregate across a corpus, never one lane on one case. The denominators alone — how many elements, crossings and unstated controls a model holds, and how many of a lane's rules ran and fired — also travel *forwards*, opening each **Lane Agent**'s input, because the separation above is one a lane cannot make about itself unless it was told the size of what it was given. Derived from the same three calls as the account behind it rather than recomputed, so the number in the instruction and the number in the report are one fact. The `*_cited` halves cannot go with them: those need drafts that do not exist yet. **Never a quota** — no number there says how many claims exist, and a lane inflating its drafts to fill one has misread it in the direction that costs more than the undercounting it fixes.
- **Scope Entry** — one unit a **Framework** considered and raised no **Claim** about, recorded on that framework's **Framework Analysis**. The positive half of an answer: dropping it leaves a reader unable to tell a unit that does not apply from one nobody looked at, which is the same distinction **Coverage** makes about lanes. **The unit is the framework's own.** The neutral answer is the **Lane**, because a lane is the only unit the service knows without reading a catalog it does not own; a package holding a requirement set answers in requirements instead. Every unit appears and the complement is never derived — a scorer holding the catalog could derive it, and a report's reader cannot. A `not-applicable` entry must state a reason. STRIDE's list is empty, which is not an omission: nothing it can analyse is out of scope.
- **Critic** — one **Framework**'s strong-model agent, reviewing the merged union of *that framework's* lane agents' output in one pass: per-claim Verdicts, cross-lane dedupe, and whatever calibration its own method asks for. **One critic per framework, and two frameworks' drafts never meet**: a critic rules its own framework's claims against its own framework's question, and a claim duplicated across two frameworks is not a duplicate — it is two methods reaching the same place, which is a result rather than a fault. Grounded in System Model facts, never free-form reflection — and never in submitter text: it templates against the same stripped model, so the only submitter words it sees are the ones a finding chose to quote. Each critic has its own bounded re-ask (`recritic/<framework>`), pinned to the same tier as the critic it corrects.
- **Verdict** — a **Critic**'s per-claim ruling: confirm, reject (with reason, kept for audit), or needs-info (kept, flagged, and saying what has to be answered). A needs-info says that in one of two spellings, and which one is true of the fact rather than a matter of taste: an **Element** and one of its attributes where the fact has a place in the **System Model**, or a plain `subject` question where it has none. The second exists because a framework may need a fact the model has no slot for — whether a policy is documented, or what code does — and a framework ruling on requirements answers mostly that kind. Pointing such a question at the nearest element and whatever attribute happens to resolve is the failure the second spelling ends: it passes every check and tells a reader nothing. Those three rules bind the fields to the `status`, which no provider schema can express, so they are checked at the review seam rather than on the way out of the **Critic**: a verdict that breaks one is the recritic re-ask's to fix, exactly like a dropped or duplicated ruling, and only a second failure ends the job. What the critic emits is therefore the unruled shape; the ruled one is built during assembly, so every verdict a report carries satisfies all three by construction.
- **Valid System Model** — one that passes the mechanical well-formedness gate (unique typed IDs, referential integrity, zone membership, legal enum values). Lane agents only ever see valid models, and one gate serves every framework: validity is a property of the model rather than of any method. An invalid extraction gets one Repair Pass — validator errors fed back to a repair node on the same tier — then the job is **rejected**, carrying the validator's issues. Rejected, not *failed*: the input never became a valid model, which is the submitter's to fix, whereas a failure is ours. Never silent auto-repair.
- **Source** — one piece of untrusted input text a job is built from: a `kind`, a caller-supplied `label`, and the `text` itself. A job carries an ordered, non-empty list of them, replacing the single `description` of earlier versions; a transcript-only job is a one-element list with no special case. `kind` is a closed vocabulary (`description`, `transcript`) and is **load-bearing** — it selects the guidance the extraction prompt renders around that source's text, so adding a kind means changing the prompt and the enum together. `label` is unique within a job, at most 200 characters, and visible to the model, and is the key a **Source Excerpt** cites, keeping the traceability chain (threat → element → the user's own words → which source) intact across N sources. Order is presentation order only: the contract makes no authority claim, so an earlier source does not override a later one. A job is bounded in **UTF-8 bytes** rather than tokens — a token cap would make the contract depend on which vendor a **Deployment**'s tiers select — by a total across all sources and a source count, both deployment config; there is no per-source byte cap, so an over-budget submission is the *sum*'s fault and the error names no single source. A source reaches a model only inside a delimiter it cannot forge — one fenced block per source, sized to the content so no submitted text can close its own block, carrying the `label` *inside* the fence so nothing caller-controlled ever sits in instruction position. That render is a pure function of the job, produced once where the graph is driven, so the service and the eval harness cannot show the same job to a model differently.
- **Source Excerpt** — a short quote from the user's input text that an Element was extracted from. Carried by every Element for traceability (claim → element → user's own words → which **Source** spoke them) and extraction evals. It travels with a `source_label` naming the Source the *quote* came from — the excerpt, not the element, since one verbatim quote has exactly one origin and an element may draw on several; where two Sources disagree the element quotes one claim and the disagreement stays in `notes`. The label is required whenever an excerpt is present and must be one of the job's labels: a citation that does not resolve asserts a traceability chain that is not there, so the validity gate checks it. An optional `source_speaker` names who spoke the quote where the text attributes it — provenance on a quote, never a role and never something a **Lane Agent** weighs — kept as its own field so a name can be stripped, which it cannot be once quoted inside the excerpt. All three fields are stripped from the model the lane agents and every **Critic** read: an excerpt answers why an element exists, which is a different question from why a claim was raised, and that second one is a **Ground**'s.
- **Element ID** — a typed, human-readable slug, unique within one System Model (one job): `<type>:<normalized-name>`, e.g. `process:auth-service`. Data Flows use `flow:<source>-to-<dest>:<label>`. Threats reference Elements by these IDs.
- **Graph Run** — one drive of a built pipeline to completion: the final session state plus one record per **node execution** (which node, the build that served it, its generation-identity fingerprint, its duration). The graph has exactly two drivers — the service over a job, the eval harness over a corpus case — and both obtain a Graph Run from the same place, so provenance never depends on which one ran. The graph cannot loop, so one drive contributes at most one record per node; a deterministic FunctionNode contributes one carrying no model. Several drives accumulated together — an eval sweep over its corpus — are where one node name carries several records. Distinct from the **Report**: a Graph Run is what happened, the report is what is served, and the run's identity fields (job ID, system name, timestamps) come from the driver rather than the graph.
- **Analysis Context** — the third thing a report records about a run, beside what each node *ran on* (**Generation Identity**) and what each finding *rests on* (**Ground**): what the service put in front of the **Lane Agents**. Four parts, recorded **in two places on the rule that a field sits where the thing it describes sits**. Two describe the run as a whole and stay on the **Report**: a digest of every LLM node's composed instruction, which is a fact about the built graph, and the **Domain Pack**s this job's model earned, which is a fact about the shared model. Two describe one framework and sit on its **Framework Analysis**: the **Candidate** rules of that package that fired, and the **Reference Note** and **Worked Case** documents those rules retrieved. The digest is taken with the job-varying placeholders unexpanded, so it identifies the repo-authored text and carries no submitted bytes; the submission's own digest is separate, and a Generation Identity says nothing about instructions at all, so two runs can share one and have been told different things. **It is context, never evidence**, and reading it as support for a claim is reading it backwards: a pack named here grounded nothing, a rule named here found nothing, and a document named here proves nothing. Recorded rather than gated — widening certification to the instructions would re-baseline every blessed pair on a prompt edit, which is a decision about what a deployment sanctions rather than a fact about a run.
- **Generation Identity** — what a fingerprint hashes: the **served** build (the identifier the provider says answered, vendor-prefixed, e.g. `vertex_ai/claude-opus-5`) joined to its tier's resolved sampling params. It is a property of the **Model Tier**, not of a graph node: the node name is not an input, so two nodes on one tier served the same build share one generation identity. Read per node *execution*, so a build that moves partway through an eval sweep yields two identities for one node — the drift signal, not a defect.
- **Report** — the complete payload a finished job serves, and the only thing a caller reads: one job's facts, one **Valid System Model**, and one **Framework Analysis** per framework the job selected. **A field sits where the thing it describes sits**, and that one rule sorted the flat schema this replaced: what describes the job or the shared model stayed on the envelope, and what describes one framework's output moved into its block. Self-containment is enforced rather than assumed — the boundary crossings are exactly the ones derived from the embedded model, the element count is that model's own, and the blocks are the job's frameworks **in order, with none dropped and none repeated**, which is the envelope's version of *no partial report*: a caller who named two frameworks and reads one has no field that would tell them which half is missing. Every claim's checks run against the shared model, once per block, over the neutral **Claim** — so a package narrowing its claims narrows what those run over and cannot opt out of them. A consumer that does not know a framework reads that neutral shape and nothing it never claimed.
- **Framework Analysis** — one **Framework**'s whole output inside a **Report**: its version, its own disclaimer, its **Claim**s and its rejected claims, its **Coverage**, its marks, and the per-framework half of **Analysis Context**. Self-contained against the one shared model and never against a second copy of it — every **Element ID** it cites resolves in the envelope's `system_model`, which is why one whole report per framework was refused: that duplicates the largest block after the findings, and nothing could check that two embedded copies of one model agreed. Its `disclaimer` is the **package's**, not the service's: the envelope's says what the service is, this one says what this framework's claims assert, and the two are different sentences the moment a report carries a framework that rules on requirement applicability rather than on attacks. The only relation between two blocks is the **Element ID** both cite; code computes that join with no model pass, which is why no cross-framework critic exists.
- **Deployment** — one installation of this service together with the configuration it runs on: the five files (`model_tiers.toml`, `sampling.toml`, `resilience.toml`, `blessed-fingerprints.toml`, `frameworks.toml`) plus the three text roots — the shared prompt bodies, the **Domain Pack**s, and one **Framework Package** per framework carried — each located by a `ANALYSIS_*` variable that picks *which* file is read and never layers a second one over it. `frameworks.toml` fixes what this install **carries**; a job selects from that set and must name its choice, and the file holds no default because a default set would make one submission mean different things on two installs with the caller reading no sign of it. Resolved **once per process** and shared by everything that runs analysis, so the HTTP service, the first-run app and an eval sweep cannot silently sit on different configurations of the same install, and the manifest a job is certified against is the same object the report route enforces — by construction, not by two loads agreeing. **A graph is built for one framework selection**, since the nodes, the state keys and the instruction digest are all functions of it, so a deployment serving several selections composes several graphs and reuses each. Loading fails closed, and the package gate runs on the same path: a deployment either has a usable configuration and well-formed packages or refuses to start. Its credentials are *not* part of it, being derived from the vendor each **Model Tier** selects.
- **Blessed** — a Generation Identity recorded in a deployment's `config/blessed-fingerprints.toml` because a sanctioned, measured run produced it. Keyed by tier. The list is deployment-local and ships empty; nothing in this repo is blessed on anyone's behalf.
- **Promotion** — the write half of Certification: taking a reviewed eval sweep and recording, in this **Deployment**'s files, the configuration it measured (`sampling.toml`, re-pinned in place) and the Generation Identities that configuration produced (`blessed-fingerprints.toml`). Its inputs are **observations, never assertions**. Every fingerprint is recomputed from the served build the sweep saw and the sampling it resolved, both read out of the run artifact's provenance block, so an operator can neither supply a fingerprint directly nor have the *requested* route stand in for the build that answered — the two are different claims, and provider-side routing is what makes the difference matter. Where one tier was answered by more than one build, promotion refuses and asks which to bless rather than choosing; the choice selects among what was observed and cannot introduce anything else. Additive: a blessed identity stays blessed until a human removes it.
- **Certification** — the three-state result of checking a run's Generation Identities against that blessed list: **certified** (every observed fingerprint is blessed), **uncertified** (at least one is not, reported by node and hash), **unexercised** (a tier the built graph declares presented no fingerprint at all). One function with two callers — the eval CLI over a sweep, and the **service** over each job it completes — so it is not "the eval gate's" result. *Unexercised* is an internal assertion rather than a routine outcome: every tier has a node that always runs, and a run producing no report is never certified. Certification never rides the report. The report carries the raw fingerprints, which are evidence and recomputable from the report alone; certification is a claim about one *deployment's* list and lives on the job record. Never called a "verdict" — that word belongs to the Critic.
- **Baseline** — a set of eval sweeps of one configuration, kept in the repository together with their reports. **Review Sitting**s and published numbers read it as their record. Its identity is computed from the sweeps, never typed by a person: the clean repository commit, the corpus digest, the requested model per tier, the resolved sampling per tier, and the framework selection. Two sweeps that agree on all five parts belong to one Baseline. The served build a provider answered with is a recorded fact about a sweep, never part of the identity.
- **Ledger** — the append-only record of what a person decided about a finding. It is the only human judgement the repository holds, and every published quality number rests on it. No row changes and no row is removed: a reviewer who changes a decision appends a new vote, and the latest vote for a `(fingerprint, voter)` pair is the live verdict, so every past state is reconstructible. Each voter's votes live in one file that carries that voter's GitHub login, so two contributors' pull requests never touch the same file, and order carries meaning only inside one voter's history. A vote stores the components of its fingerprint, so a better match rule re-keys the ledger by recomputation and costs no re-vote.
- **Review Sitting** — one vote session over a **Baseline**: a person reads its reports, decides on each finding, and appends votes to the **Ledger**. `evals/VOTING.md` holds the procedure. A Review Sitting produces votes and nothing else. It never signs off a corpus case — that act is a **Case Sitting**.
- **Case Sitting** — one person's read of one corpus case: the sources, the blessed **System Model** and every declared framework's reference set, together in one session. The reader writes their own threat list before they open the recorded sets, so the sets are tested rather than confirmed. The record is an append-only entry in the case's metadata: the reader's GitHub login, the date, a digest of each file read, and the name of the committed, filled reading document. A Case Sitting from any rostered person takes the case off the unreviewed list, and the **Standing** roster labels the read. A change to a read file puts the case back on the list. `evals/BLESSING.md` step 6 defines the method.
- **Draft Sitting** — a **Case Sitting** a reader started and did not yet submit. It holds the reader's own threat list, their marks, their missing list and their notes. It also holds a digest of each required file as it stood when the draft opened, and, once the reader records the sitting, the entry that record appended and the unreviewed line it removed — which is what a reader who holds the case back from a submission puts back. **It lives outside the repository and never merges**: that is what keeps an unsigned own list out of a pull request. It is `open` until the reader records the sitting, then `finished` until they submit. Recording the sitting still appends the entry to the case's metadata, so a Draft Sitting is not a record and signs nothing; a successful submit deletes it. **A finished draft re-opens its case**, because the draft is what makes a case re-openable and not the signature: the reader records the case again, and the second record replaces the entry the first one appended.
- **Standing** — the class a person's judgement carries: `maintainer` or `contributor`. A person has one standing, whatever they submit — a vote, a **Case Sitting** or a baseline sweep. The standing lives in a checked-in roster keyed by GitHub login, never on a vote row or on a manifest entry, so a promotion re-classes that person's whole history at once and rewrites no row. Every published number states which standings it includes; contributor judgements stay a second series until a maintainer promotes them.
- **Model Tier** — one of exactly two vendor-neutral capability classes every LLM node runs on: **`base`** (the workhorse: extraction and repair) and **`strong`** (judgement: every framework's **Lane Agent**s, its **Critic**, and its recritic re-ask). The keys are per framework rather than per lane — `analyze/<framework>`, `critic/<framework>`, `recritic/<framework>` — because a framework's lanes all run the same judgement on the same tier, and what an operator actually chooses between is running one framework's analysis cheaper than another's; a `recritic` is required to resolve to its own `critic`'s tier, since a re-ask on a cheaper model than the pass it corrects is the failure that pairing exists to stop. Names are on a capability axis, not a vendor's product line — `strong` matches the critic's "strong-model" description; the prior `flash`/`pro` were Gemini product names. Each tier independently selects its `(vendor, model)`, so `base` and `strong` may run different vendors at once. Auth is *derived* from the vendor, never configured alongside it — each vendor owns its credential mode, so an unrepresentable pairing like `vertex + api_key` cannot be written down.
- **Provider Capability** — what one `(vendor, model)` pair will accept, in exactly three states: **supported** (the provider accepts it, and the pinned model map is what says so), **unsupported** (the provider rejects it), **unknown** (the pinned map carries no entry for the model, so nothing here has an answer). The third state is the load-bearing one and is never collapsed into the second: LiteLLM answers for an unmapped model out of the provider's *base* config rather than declining, so "rejected" and "never heard of it" reach a raise/no-raise gate as the same non-raise. That fallback is correct for a **Model Gate**, whose job is to refuse a binding rather than to know things, and becomes a false assurance the moment it is reported as a checked answer. A pair reporting `unknown` still binds — refusing to run a model the map has not caught up with is the worse failure — but nothing has verified it. Capabilities legitimately differ between providers and are never equalised: inventing a default for an unsupported control, or emulating one without disclosure, is the failure this vocabulary exists to name.
- **Provider Conformance** — whether the *application* behaves equivalently on a given provider, which is a different question from how good that provider's threat models are. Conformance is deterministic, is asserted for every supported vendor equally, and covers binding, the build-time gates, sampling resolution, **Generation Identity**, and the report schema; **model quality** is empirical, lives in `evals/`, and is expected to differ. A vendor never fails conformance for scoring lower than another. The suite is **credential-free** by construction — capabilities come from the pinned model map and bindings are built against a declared-but-fake environment — which is what lets it run for all three vendors in the offline lane rather than only where credentials happen to exist. Its limit is exactly as important as its coverage: it establishes what a provider *would be asked for*, never that a provider has served a request. Answering that second question is the **Provider Smoke**'s job, and where its credentials are absent the coverage remains **unexercised** in the sense Certification already gives the word, reported as such rather than left to a green check to imply.
- **Provider Smoke** — one small system, once, through the shipped graph, on the pair a deployment selects: the cheapest run that can show a provider actually served this application. It runs **every framework the deployment carries**, since each brings its own tier keys that an operator may point at different vendors, and smoking one while reporting green would leave another's binding unexercised. It answers eight questions and no others — binding, structured extraction, lane-agent and critic output, sampling acceptance, served-model capture, **Generation Identity**, and a provenance record that recomputes from itself — and it answers them for every supported vendor on the same trigger, because coverage that exists only where credentials happen to exist is how one vendor comes to be better assured than the others. Its answers are three-valued for the same reason **Provider Capability**'s are: a question the provider left unanswered (a response carrying no served build) reports `unknown` and fails nothing, since the application handled the difference correctly. It is not an eval and never grades a threat model — a vendor whose analysis is weaker passes the smoke, and a vendor that has not run one is unexercised rather than failing.
