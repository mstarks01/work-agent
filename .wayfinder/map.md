# Map: Agentic STRIDE Threat-Modeling Workflow

Label: `wayfinder:map`
Tickets live in `.wayfinder/tickets/` as child issues. A ticket is claimed by setting its `assignee:` frontmatter; open+unassigned+unblocked = frontier.

## Destination

A production-quality STRIDE threat-modeling service in this repo: Python, Google ADK graph-based multi-agent workflow, self-owned container on Cloud Run behind Ping-authenticated endpoints. Front-end submits semi-structured text one-shot, receives a job handle, polls/streams until a structured JSON report (per-element threats + severity + mitigations, traceable to input elements) is ready. Shipping includes a golden-case eval suite in CI.

## Notes

- Language: Python. Always consult the `python-style` skill when writing Python and the `owasp-security` skill for security-relevant code.
- **Execution is carried into this map** (destination is a full production build): once design tickets close, implementation tickets graduate from the fog.
- Per-agent Vertex model selection is a hard requirement (e.g., Flash for extraction, stronger models for analysis). Token/context optimization is a standing preference.
- Prompts and skills load from a directory of files via this repo's own loader interface — one implementation, shipped as `MarkdownLoader` with `SkillLoader` kept as an alias (no external PromptLoader exists to mirror; see [Obtain existing PromptLoader interface](tickets/011-prompt-loader-interface.md)).
- **Deterministic decisions belong in code; models are used only for judgement decisions not easily handled by deterministic code.** Standing principle across the whole application — split every node's checks into mechanical (validators, FunctionNode bookends, lints) and judgement (what the prompt addresses).
- Commits: no AI attribution trailers. User prefers concise communication.

## Decisions so far

- Deployment boundary — Cloud Run (own container; Agent Engine rejected: IAM-only endpoint auth can't front Ping, logging constrained to stdlib/Cloud Logging paths, Agent Identity pre-GA).
- Input shape — hybrid: semi-structured front-end text normalized by a cheap extraction agent into a canonical system model.
- Interaction model — one-shot with async delivery (job handle, poll/stream progress; no mid-run user input).
- Output — structured JSON: per-element STRIDE threats with severity + mitigations, traceable to input flows/endpoints.
- Quality bar — golden-case eval suite in CI; cases bootstrapped from OWASP Threat Model Cookbook + internal systems, SME-blessed once.

- [Assemble the ADK graph](tickets/021-adk-graph-assembly.md) — shipped as `stride_service.graph` (topology, node functions, `build_pipeline`) + `stride_service.pipeline` (`AdkPipelineRunner`, filling the ticket-018 seam; `create_app()` now defaults to it), on `google-adk==2.5.0`. **`output_schema` on workflow `LlmAgent`s is supported** — verified in the installed package, so ticket 013's assumption holds and the raw-emission fallback was not built; the cost is that a schema-violating emission fails the job instead of routing to `repair`, which is the right disposition now that `response_schema` is enforced at decode time. Topology as decided plus three structural nodes: `revalidate` (a second node over the same validate function, so the one-repair budget is acyclic rather than counted), `reject` (terminal), and `merge` (`join_drafts` behind ADK's code-free `JoinNode` barrier). `{category}` is filled at build time — six parallel analysts cannot share one state key — while the six job-varying placeholders ride *rendered* state keys, guarded by a lint that no other `{identifier}` survives composition. Models bind through an injected `resolve_model`, so the entire graph runs offline against scripted `BaseLlm` stand-ins: 34 new tests cover wiring, every node function, and end-to-end runs of the clean, repaired, rejected, and fail-closed paths. Suite 302 green.

- [Golden-case eval suite design](tickets/009-eval-suite-design.md) — a golden case is a **two-artifact** fixture (blessed `SystemModel` + `ReferenceThreat` set against its IDs), giving three eval modes from one corpus and per-node attribution of every regression; models bootstrapped from `extract` then SME-corrected against the *source text* (anchoring risk recorded). Cases stay 8–20 elements so ground truth is exhaustively enumerable — non-exhaustive references silently corrupt precision. Corpus of 12 built around a **payments control case** plus far-domain systems, because exemplar-domain bias is only measurable as a *delta*. Scoring is mechanical-first: lane prefilter → per-pair judge on `claim` equivalence → bipartite assignment → three-bucket adjudication of unmatched threats (`ungrounded` alone gates; "unmatched = FP" rejected as pushing toward under-reporting), with element agreement *scored, never filtered*, and severity calibration pure arithmetic. `pro` judge, pinned separately from the tiers, ≥90% human-agreement bar — numbers are judge-relative and must not be quoted as absolutes. Sampling config becomes a versioned knob shared by eval and prod (default `0`), with the temperature/Self-MoA question deferred to measurement. Thresholds: Tier 1 structural gates day one, Tier 2 must-find recall is per-case, Tier 3 are regression ratchets — mechanism decided now, numbers derived from ~5 baseline sweeps. CI splits credential-free offline evals (every PR) from WIF-authenticated live evals (path-filtered + scheduled sweep); `pull_request_target` prohibited. Cost is ~$0.30/case — quota and nondeterminism bind, not dollars. Graduated tickets 022 → 023 → 024 → 025, with phase 1 cut to 6 cases and structural-only gating because the binding cost is serialized SME time.

- [Context optimization strategy](tickets/010-context-optimization.md) — measured first: a 20-element case gives the critic ≈16K tokens against a million-token context, so **context economy is not a live problem at the designed sizes** and the strategy is to *bound* inputs, not compress them. Six decisions: (1) **no per-analyst element view** — ticket 004's mechanical pre-filter is *cancelled*, not deferred, since a correct filter is nearly the whole model anyway while breaking cross-lane citation and the critic's dedupe grounding; all six `## Applicability` openers reworded from "your element view is mechanically pre-filtered" (a promise `prepare_analysis` never kept) to scoping only where a threat may be *filed*, guarded by a new lint. (2) **150-element admission cap** in `validate` as a `too-many-elements` issue returning alone, landing the job in the existing `rejected` state before any analyst spend — a blast-radius guard, not a calibrated threshold. (3) **Dual-key state ratified** with the invariant that a *rendered* key is written once by the FunctionNode deriving it and never read by Python — both copies kept so a failed job can be read back exactly as the model saw it. (4) **Implicit caching only**: the six analysts share no prefix *with each other*, so caching pays only across jobs for one category — explicit `CachedContent` would buy 7 billed resources and a stale-prompt hazard against traffic we haven't measured. (5) **The shipped 100 KiB request cap stands** (ticket 008), ratified rather than renumbered. (6) **No compaction anywhere** — everything summarization would drop is something the report must cite, and stripping the critic's `justification` view would break a shipped judgement step. 7 new tests, suite 308 green.

- [Author the phase-1 golden corpus and SME blessing workflow](tickets/022-author-golden-corpus.md) — shipped `evals/`: six cases (8–20 elements each, all passing the shipped validator), **109 reference threats** (61 must-find), **129 hand-labelled judge pairs** (76/53, weighted to hard negatives), the `BLESSING.md` workflow, and `verify_corpus.py` — the credential-free lint spec ticket 023 ports, importing its vocabularies from `report.py`/`validation.py` so the corpus cannot drift from the shipped schema. Case 01 is the payments **control**; the four far cases each carry a trust shape the exemplar has no instance of, and cases 05/06 are real OWASP cookbook entries (CC-BY 4.0, attributed), 06 converted as a scoped subset because the source diagram is 32 elements. **One departure from decision 2, confirmed with the user:** no Vertex credentials exist here, so candidate models came from an agent stand-in running `prompts/extract.md` — blessed models are unaffected (blessing is against the *source text*), but the diffs are signal about the prompt, not the pinned model, and re-bootstrapping is now a line item on [Eval phase 2](tickets/025-eval-phase-2.md). The 37 recorded corrections are already an error taxonomy: the most repeated failure is a **stated qualifier stranded in `source_excerpt`** and never reaching an attribute analysts read, and the most alarming is a single **invented absence** — a control asserted missing rather than unknown. Unblocks [Implement the eval harness, ReferenceThreat, and scorer](tickets/023-implement-eval-harness.md).

## Not yet specified

- Observability: wiring the custom logging library, tracing/OTel across graph nodes. Carries one concrete item from [Context optimization strategy](tickets/010-context-optimization.md): capture `cached_content_token_count` from Vertex usage metadata per node, so the deferred explicit-caching question is settled by a measured hit rate rather than argued.
- ADK session backend: the graph runs on `InMemorySessionService`, which is per-process and lost on restart. Cloud Run wants an async `session_service_uri` (see [Research: ADK graph features](tickets/002-research-adk-graph.md)); the `AdkPipelineRunner` takes one by constructor argument, so this is a backend choice, and it pairs naturally with the job-store backend below. Sizing fact from [Context optimization strategy](tickets/010-context-optimization.md): session state deliberately holds every artifact twice (structured for code, rendered for prompts), so a persisted backend pays ~2x per job — bounded by the 150-element cap, but worth knowing before choosing a store.
- Per-node sampling config: no `GenerateContentConfig` is set, so every node runs on ADK's defaults for temperature and thinking budget. Pinned model strings buy eval reproducibility (ticket 007) that default sampling partly gives back. **Half-decided**: [Golden-case eval suite design](tickets/009-eval-suite-design.md) settled that temperature is a *versioned config value shared by eval and production* (default `0`, a knob rather than a constant) — implemented in [Implement the eval harness](tickets/023-implement-eval-harness.md). The *value* stays open on purpose: temperature 0 plausibly amplifies exemplar anchoring and forecloses the Self-MoA recall lever, so [Eval phase 2](tickets/025-eval-phase-2.md) measures 0 vs. default vs. k=3 rather than arguing it. Thinking budget remains wholly unspecified.
- Where analysis quality decays with model size: the 150-element admission cap from [Context optimization strategy](tickets/010-context-optimization.md) is a blast-radius guard chosen with no evidence behind it — the golden corpus is 8-20 elements by design, so nothing measures how a single-pass critic dedupes 200+ drafts, or where per-analyst recall falls off on a large model. Belongs to [Eval phase 2](tickets/025-eval-phase-2.md) as a sweep over model size; the cap is a parameter of `validate()` precisely so it can move on evidence.
- Error handling in the graph: partial results, retries, timeouts, poison inputs.
- CI/CD pipeline and Cloud Run deployment details (Ping middleware specifics follow org patterns). **The CI half is now specified** by [Golden-case eval suite design](tickets/009-eval-suite-design.md) and owned by [Wire the eval suite into GitHub Actions CI](tickets/024-ci-wiring-evals.md): GitHub, no forks, OIDC→WIF with a separate eval service account, offline/live job split, `pull_request_target` prohibited. Note there is still **no `.github/` and no git remote** — 024 stands CI up from nothing. Deployment (image build, Cloud Run release, Ping middleware) stays fog.
- Job store backend and retention TTL (report JSON at rest; contract reserves 404-after-expiry — see [Front-end API contract](tickets/008-api-contract.md)). The `JobStore` seam and an in-memory implementation now exist, so this is a choice of backend behind a settled interface.
- Cost/quota controls per model tier.
- Technology-domain skill packs: authoring + the pack-selection rule table in `prepare` — graduate when evals show domain-specific recall gaps.
- Exemplar-domain bias: all 18 analyst exemplars are anchored on one fictional payment service (the shared miniature system in `analyst.md`, chosen for spanning three zones with a hook per category — see [Author agent prompt files and category exemplars](tickets/019-author-prompt-files.md)). Few-shot anchoring on a single domain can bias recall toward its threat shapes, so systems unlike it — IoT fleets, data pipelines, ML services — may analyze measurably worse. A known risk to *measure*, not to pre-solve — and the measurement is now designed. [Golden-case eval suite design](tickets/009-eval-suite-design.md) makes it observable as a **delta**, not an absolute: the corpus carries exactly one payments control case near-identical in shape to the exemplar plus at least three far-domain systems (IoT fleet, batch pipeline, ML service), and the near-vs-far recall gap is a tracked, deliberately non-gating number (a large delta is a finding to act on, not a build to break). The corpus that measures it now exists: [Author the phase-1 golden corpus](tickets/022-author-golden-corpus.md) shipped the payments control (`01-payments-checkout`) alongside four far-domain cases chosen so each carries a trust shape the exemplar has no instance of — physically accessible devices with one shared credential, file provenance instead of caller identity, an artifact loaded as code, an async queue as the trust hand-off, and the operator's own code on hardware it does not control. All that remains is running it: the delta lands in [Eval phase 2](tickets/025-eval-phase-2.md), and stays deliberately non-gating. Cheap to fix if confirmed — exemplars live in their own subtree so they can be retuned or diversified without touching the shared procedure or output contract — and it overlaps the domain-pack line above.
