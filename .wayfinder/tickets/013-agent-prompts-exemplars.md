## Question

Author the prompt set for every LLM node in the decided topology — extract, repair, the six category analysts, and the critic — loaded via the PromptLoader directory pattern. The research (ticket 001) found few-shot exemplars and structure drive threat-modeling recall more than topology, and named the documented failure modes to write exemplars against: second-order threats and wrong threat perspective. Decide the split between prompt content and skill content (per ticket 006's design), the exemplar set per STRIDE category, and the critic's grounded checklist format (verdicts against element facts, not free-form review).

## Resolution

Resolved 2026-07-20 via grilling, grounded in tickets 001 (exemplars drive recall), 004 (topology), 006 (skill anatomy), 011 (loader is canonical), and the shipped `stride_service` package.

1. **Prompt/skill split.** The skill is *what to know*; the prompt is *what to do with this job's input*. A prompt owns role framing, the I/O contract, the ordered procedure, few-shot exemplars, and the ADK state placeholders. Guardrails deliberately stay skill-side only — duplicating them into prompts would reintroduce drift.
2. **One analyst prompt, not six.** The six analysts differ only in category name and exemplars, so a single templated `analyst.md` body carries role/procedure/output contract and the category is injected by ADK state templating (the loader stays templating-free per ticket 011). Prevents the output contract drifting across six copies, mirrors the shipped `compose_analyst_skills` shape, and keeps the longest common cacheable prefix for ticket 010.
3. **Loader naming.** Reuse, not duplication: rename the shipped loader to a neutral `MarkdownLoader` (+ `MarkdownNotFoundError`/`MarkdownFormatError`) in `stride_service/markdown_loader.py`, keeping `SkillLoader` as an alias so the three closed tickets that depend on it stay green. One implementation, two vocabularies; a subclassed `PromptLoader` was rejected as an invitation to divergence, and reusing `SkillLoader` verbatim was rejected because `SkillNotFoundError` on a missing *prompt* is a small lie that costs debugging time. Composition stays domain-split: `skills.py` keeps `compose_analyst_skills`, a new `prompts.py` gets `compose_analyst_prompt`.
4. **Layout and fixed sections.** `prompts/{extract,repair,analyst,critic}.md` plus `prompts/exemplars/<category>.md` ×6. Four fixed H2 headings, lint-enforced as exact strings: `Role`, `Input`, `Procedure`, `Output`. Exemplars live in their own subtree because they are the part tuned repeatedly once ticket 009's evals show recall gaps — separating them means tuning never risks touching the shared procedure or contract. Exemplar files use the exemplar's unique name as its H2 (`split_sections` raises on duplicate headings).
5. **`DraftThreat` — a gap this ticket surfaced.** Analysts cannot emit a `Threat`: `verdict` is the critic's ruling and `confidence` is explicitly critic-calibrated. A new `DraftThreat` model carries the seven analyst-owned fields (`id`, `category`, `title`, `description`, `affected_element_ids`, `severity`, `mitigations`); the critic maps `list[DraftThreat]` → `list[Threat]` + `rejected_threats`. Placeholder verdicts were rejected outright: an unreviewed threat that ships looking reviewed would pass `Verdict._check_shape` undetected.
6. **The output contract lives in three places, each with one owner.** Pydantic (`DraftThreat.model_json_schema()`, bound as the node's output schema) owns the machine-enforced shape; the prompt's `## Output` owns semantics in prose only, **no JSON**; the exemplars own the concrete shape. The drift guard: the prompt lint parses every fenced `json` block in `prompts/exemplars/*.md` through `DraftThreat`, so renaming a field in `report.py` fails CI on all six exemplar files. *Unverified:* the ADK research notes confirm input-schema validation for `LlmAgent` workflow nodes at 2.5.0 but say nothing about `output_schema` — confirm at graph-wiring time; the fallback is parsing `DraftThreat` from the raw emission via the repair path, which leaves lints and exemplars unchanged.
7. **Three exemplars per category:** canonical (clean trigger, well-formed threat, attacker-action phrasing), second-order (low-value element as foothold, impact scored across the reachable set), and unknown-conditional (cites the `unknown` attribute rather than asserting the control is absent). Wrong-perspective — the second documented failure mode — is taught by prose contrast inside the exemplar body, never as a badly-phrased threat in a fenced block the model might imitate; the one-JSON-block-per-section lint enforces this structurally. One shared miniature system model lives in `analyst.md`'s `## Input` and all eighteen exemplars cite its element/flow IDs: paid for once in the cached prefix instead of eighteen times, and it makes the six lane boundaries directly comparable on the same system.
8. **Critic checklist.** Mechanical checks move to code in the join/assemble `FunctionNode` — element-ID resolution, category-letter match, verdict-shape consistency (the latter two already exist as validators). The LLM critic runs five judgment steps in fixed order per threat: evidence (trigger attribute actually present as claimed; `unknown` → `needs-info` with `related_unknowns`), lane (misfiled threats rejected, never silently recategorized), duplicate (same attacker action against same element), severity calibration against the shared rubric, confidence. Steps 1-3 gate; 4-5 run on survivors. All six analysts' drafts arrive in **one** call — cross-category dedupe is impossible otherwise.
9. **`extract`** emits `SystemModel` with `unknown` as the *default* rather than a fallback; any inferred value is written to the attribute **and** recorded in `assumptions` (an inference absent from `assumptions` is a bug, stated in those terms). Two exemplars inline in `extract.md` — sparse input yielding heavy `unknown` usage, and a legitimate inference correctly recorded. **`repair`** takes the prior JSON, the `ValidationIssue` list, **and the original input text** (without it, repair's only legal move on an out-of-vocabulary tag is to blank the field, losing information the source contained); minimal diff touching only what the issues cite; never invents a fact to satisfy a rule — `unknown` plus an assumption instead; one pass, then rejection with issues surfaced per the ticket-008 contract.
10. **Caps and lints.** Build-time only, enforced by `tests/test_prompt_lints.py` via `estimate_tokens` — a violation is a red build, and there is no runtime truncation path anywhere. `analyst.md` ≤2000, `exemplars/<category>.md` ≤1500, `critic.md` ≤1500, `extract.md` ≤1500, `repair.md` ≤800, putting the worst-case analyst instruction at ≈5.7K against ticket 006's 6-8K envelope. Six lints: four bodies with the exact four headings in order and non-empty; exemplar filenames derived from `StrideCategory`; ≥3 sections per exemplar file each with exactly one fenced `json` block; every block parsing as `DraftThreat`; caps; no stray files under `prompts/`.

**Standing principle established, beyond this ticket:** deterministic decisions belong in code; models are used only for judgement decisions not easily handled by deterministic code. Recorded in the map's Notes.

**Noted, not solved here:** the caps cover only the static instruction side. Per-job data (System Model, the six analysts' drafts) is unbounded and unguarded; oversize would surface as a loud Vertex context-length error, not a silent partial analysis. The critic is the pressure point as the one node seeing all six analysts' output at once. Belongs to [Context optimization strategy](010-context-optimization.md). Also note `estimate_tokens` is a coarse words×4/3 estimate that reads low on fenced JSON — the headroom absorbs it, but the number is not exact.
