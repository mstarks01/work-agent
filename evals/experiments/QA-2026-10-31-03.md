# QA-2026-10-31-03: how well does extraction read a Mermaid diagram?

Scope: the first measurement of the `diagram` source kind (#2056). Mode audit,
one grant of $1.00, $0.7475 metered at list price (an upper bound).

**Status: closed.** E1 is supported: extraction lost about half as many
elements from a clean diagram as from the description.

## Before the experiment

1. **The open question.** A `diagram` source reaches extraction with one
   register sentence and no change to `extract.md`. Nobody measured how well
   extraction reads one. The answer decides whether the register needs work
   before the web app offers diagram upload as an equal to a description.
2. **The suspected mechanism.** A clean diagram names each element and each
   flow exactly, so extraction should find them at least as well as from
   prose. Two things can go wrong: the register says that a shape states no
   attribute, so an element's type can come out wrong; and a subgraph is a
   trust zone only where its label says so, so a zone can be missed.
3. **The change under test.** None. This measures the shipped route on a new
   input kind.
4. **The outcome.** Extraction figures only: the fate of each blessed element.
   No downstream report figure.
5. **The falsifier.** The diagram arm's mean elements lost per sweep exceeds
   the description arm's mean by more than half of the description arm's
   standard deviation.
6. **The smallest experiment.** Two arms on one commit, one route and one day,
   run in turn:
   - **description:** `run --mode extraction` over `evals/corpus` as it is;
   - **diagram:** the same over the corpus that `QA-2026-10-31-03/build_corpus.py`
     writes, where each case's one source is its `evals/diagrams/<case>.mmd`.
   All 16 cases, four sweeps on each side, `gpt-5.6-luna` through OpenRouter,
   three cases in flight, the arms in turn. Each sweep is replayed alone with `run.py replay` over
   `evals/corpus`, which holds the same blessed models as the diagram corpus.
7. **Cost and acceptance.**
   - QA-2026-10-17-01 spent $0.471 on ten 16-case sweeps on this route, about
     $0.05 a sweep. The estimate for ten sweeps is $0.50.
   - A pre-flight of one case on the diagram arm comes first, and its cost and
     provenance are read before any sweep.
   - **Amended after the pre-flight, before any sweep.** The route has no
     price table, so the spend hold cannot run (`--accept-cost unknown`). The
     meter is each artifact's token counts at OpenRouter's public list price
     for `gpt-5.6-luna` ($0.20 a million input tokens, $1.20 a million output
     tokens, $0.25 a million cache writes). That is an upper bound. The
     pre-flight read $0.0056 for one case, and an archived description sweep
     reads about $0.10 at list price. So each arm runs four sweeps, not five:
     about $0.77 at list price in all.
   - A sweep that would take the spend past $0.95 at its estimate does not
     start. An arm that stops short is incomplete, not passing.

## The gate

**Elements lost** in a sweep is the sum of the six loss fates that `replay`
prints: `mistyped`, `misattached`, `endpoint_unaligned`, `omitted`,
`ambiguous` and `unresolved`. `found`, `renamed` and `placeholder` are not
losses.

| Result | Reading |
| --- | --- |
| diagram mean ≤ description mean + 0.5 description sd | supported: extraction reads a clean diagram at least as well as the description |
| diagram mean > description mean + 0.5 description sd | refuted: the register or the diagram loses elements |
| an arm with fewer than four complete sweeps | inconclusive |

**Read, not gated:** `mistyped` alone, `placeholder`, the wrong facts on
paired elements by attribute, the emissions that the gate refused, and the
cost of each arm. A diagram states no control attribute, so the diagram arm is
expected to have more wrong or unknown facts. That figure says how many more
questions a diagram-only job asks; it is not a loss of the register.

**What each result changes.**
- Supported: diagram input reads cleanly; the next work is a hand-drawn set,
  because these files are an upper bound.
- Refuted: the losses by fate name the register sentence to change, and that
  change is a new experiment.
- Inconclusive: no decision; the spend so far is recorded.

## E1 result

Elements lost per sweep, from `run.py replay` over `evals/corpus`:

| Arm | Sweeps | Mean | sd |
| --- | --- | --- | --- |
| description | 14, 14, 20, 11 | 14.75 | 3.77 |
| diagram | 9, 5, 11, 6 | 7.75 | 2.75 |

The gate line was 14.75 + 0.5 × 3.77 = 16.6, so the hypothesis is supported.

Read, not gated (per sweep):

| Figure | description | diagram |
| --- | --- | --- |
| `placeholder` (a trust zone not found) | 12.0 | 0.0 |
| `renamed` | 110.2 | 14.0 |
| `mistyped` | 0.5 | 2.75 |
| `endpoint_unaligned` | 3.8 | 4.0 |
| wrong facts on paired elements | 204 | 282 |
| cases the gate refused | 0.5 | 0.5 |
| metered cost | $0.101 | $0.084 |

- **What the diagram did well.** The `Trust zone:` label placed every zone,
  and the exact names left almost nothing to rename.
- **Where the diagram lost elements.** Nearly all its losses are a wrong
  element type and the flows that end at that element: case 10's CDN and case
  02's sensor node typed as a Process, case 09's catalogue spreadsheet typed as
  an External Entity, and case 03's data analyst. Each shape named the blessed
  type, but the register says that the shape of a node states no attribute.
  A register sentence that lets the export's shapes state the element type is
  the next candidate. It is a new experiment, and it needs its own grant.
- **What a diagram cannot state.** The wrong facts rise mostly in
  `flow.authentication` (25 to 114), `process.interface_kind` (41 to 83) and
  `process.exposure` (23 to 65). A diagram-only job leaves these unknown, so
  its pause asks more questions.
- **Limits.** The diagrams are the export of each blessed model, so this is an
  upper bound for a drawn diagram. The spend is metered from the artifacts'
  token counts at list price; no billed figure was read.
