# QA-2026-10-13-09: one choice for every capability question answered "no"

A job that selects ASVS asks a capability question for each capability its
rule needs and no answer states: 30 on the example description at level 2,
10 at level 1 (read off `QA-2026-10-13-08`'s checkpoint). A description
cannot close one, because only an answer states a capability (ADR 0051). By
one reading, the example states about 10 of the 30 as present (`authentication`,
`oauth`, `browser-frontend`, `tls-use`, `database`, `encryption`,
`restricted-access`, `sensitive-http-requests`, `external-facing-http-services`,
`browser-accessible-http`) and none of the other 20.

The maintainer chose to let one choice answer "no" to the capability
questions left, and then chose its layout from the three below. The audit
spent nothing: `run.py early-policies` walks the archived reports offline
(186 STRIDE reports and 32 ASVS reports, `--root` the main checkout's
`evals/`).

## The walk (E1)

Each layout answers "yes" to a share of a list's capability questions, each
on its own, and then answers "no" to every capability question of the list
left in one choice. The walk does not know which capabilities an
application has, so it reads three shares: none, a third (about the example's)
and all. Every other question is charged as `group-question` charges it.

| Layout | File |
| --- | --- |

| One box at the first capability question's place | `QA-2026-10-13-09/early-policies-first-box.json` |

`no-to-the-rest` loses to `group-question` in no cell, at any of the three
shares. With no "yes", ASVS alone settles 1,860 units at five choices, and
the whole STRIDE list with both frameworks costs 3,658 choices. With every
answer "yes", it is `group-question`.

The first box puts every "yes" before STRIDE's turns, as gathering the
capabilities did in `QA-2026-10-13-02-E2`. The last box puts them after
STRIDE's groups, so ASVS waits. The maintainer chose `no-to-the-rest`.

The walk answers truthfully: it does not measure how often an owner answers
"no" to a capability the application has.

## The two boxes

The first box was a policy of `evals/harness/early_policies.py` while the
audit ran; the shipped policy replaced it. Both boxes, as they ran:

```python
def first_box(model, frameworks, yes_share):
    """Every capability question of a list in one box at the first one's place."""
    charges = []
    for shown in _lists(model, frameworks):
        boxed = [q for q in shown if q.group == CAPABILITY_GROUP]
        for group, rows in groupby(shown, key=lambda q: q.group):
            run = list(rows)
            if group != CAPABILITY_GROUP:
                charges.append(Charge(max(q.decisions for q in run), frozenset(q.key for q in run)))
            elif run[0] is boxed[0]:
                charges += box(boxed, yes_share)
    return charges


def box(rows, yes_share):
    """Each "yes" on its own, from the top, then one "no" for every row left."""
    count = round(len(rows) * yes_share)
    charges = _each(rows[:count])
    if rows[count:]:
        charges.append(Charge(1, frozenset(q.key for q in rows[count:])))
    return charges
```

The last box is the same with `run[-1] is boxed[-1]` in place of
`run[0] is boxed[0]`.

A first model charged the whole box as one charge of a choice for each "yes"
and one for the rest. `_spend` stops at the first charge over the budget, so
a box of eleven choices stopped a five-choice submitter at the top of the
list. An owner can answer part of a box, so each "yes" is its own charge.
