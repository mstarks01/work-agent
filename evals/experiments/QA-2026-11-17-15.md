## Answers

**What is hurting report quality?** Nothing measured here. The code between the critic and the report, and between the lanes and the critic, loses no draft and no proposal on the archived runs that today's code can read. Two observed defects were in a report validator and an eval reader. Both were latent: no archived report holds a returned claim.

**Which phase is responsible?** None. These checks find no loss in fan-in or reporting. The historical evidence does not make assembly the leading recall bottleneck.

**What was changed?** Seven PRs:
- standing instruments for assembly and fan-in accounting;
- a severity oracle;
- a fix in the block's identity check;
- a fix in the critic replay;
- a regression matrix with scripted-graph tests;
- the deferred proposal IDs on the fan-in's result.

**What did not work?** Nothing that was tried lost. A severity comparison without the ancestry gate would read 133 historical differences as defects. All 133 come from runs before #1208, when the critic set severity, so the gate is required.

**What remains untested or blocked?** These questions have no oracle:
- whether a critic's verdict is right;
- whether a drop reason is true;
- whether a swap that moves its verdict is wrong;
- whether a kept claim on a unit that a Control row kept should have been returned.

The 101 incompatible fan-in blocks and the 1,170 unavailable assembly drafts are unmeasured, not clean.

**What should the next audit do first?** Run `run.py assembly` and `run.py fan-in` on the next sweep. Code drift since the archived runs makes most older blocks incompatible, so a fresh sweep is the only way to grow the compatible denominator.

## Limits

- Every count is an observed count on archived runs. None is an error rate for live runs.
- Zero unexplained omissions and zero wrong dispositions are the acceptance targets. They hold on the compatible archive, and they are not measured beyond it.
- The scripted tests prove that each fault is detected. They do not prove semantic correctness.
