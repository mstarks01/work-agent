# QA-2026-10-14-02: the promotion gate of the capability reader

ADR 0086 declared the gate before this run: the reader's default turns on only
if, on one run of the node on each holdout case, at least 95% of the statements
the maintainer rules right or wrong are right.

`gate.py` uses the node's own prompt (`compose_capabilities_prompt`), the
sources rendered as the service renders them (`render_sources`), and the
node's own check (`with_stated_capabilities`). It does not run the node as a
job runs it, in three ways:

- The call asks for a JSON object. A job sends the node's `CapabilityReading`
  schema to the provider.
- The call sends the whole prompt as one user message. A job sends the prompt
  as the node's instruction, which reaches the provider as a system message.
- The check runs over each case's reference `model.json`, which states no
  capability. A job runs it over the Valid System Model after the capabilities
  that closed fields prove are written (ADR 0085), and the check drops a row
  that names one of them.

`gpt-5.6-luna` on OpenAI, one call on each of `14-loyalty-oauth-platform` and
`15-multitenant-invoicing`, $0.0103 of a $0.02 grant at the offline map's
rates. The run spent the last read of both holdout cases.

## The gate (E1)

The node kept 35 statements on case 14 and 29 on case 15, and dropped one row
on case 14 whose quote was not in the source (`gate-runs.json`). The
maintainer ruled all 64 (`ballot-issued.csv`, returned as
`ballot-returned.csv`; every carried column unchanged):

| Case | Right | Wrong | Unsure |
| --- | --- | --- | --- |
| 14-loyalty-oauth-platform | 35 | 0 | 0 |
| 15-multitenant-invoicing | 28 | 1 | 0 |
| Both | 63 | 1 | 0 |

Precision is 98.4%, so the gate passes. The one wrong statement is
`multi-factor-authentication` on case 15, `too-specific`: support agents sign
in with an account and a one-time code, which shows one-time codes
(ruled right) but not a second factor.
